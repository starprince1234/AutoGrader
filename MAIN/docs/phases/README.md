# 阶段文档

阶段文档记录**一个开发阶段真实做了什么、验证了什么、还剩下什么**。它是"项目是否真的在推进"的唯一证据来源。

## 目录

| 位置 | 内容 |
|---|---|
| `active/` | 当前进行的阶段，每个阶段一份主记录 `phase-NN-short-title.md` |
| `archive/` | 已归档阶段（索引见 `archive/README.md`） |

## 阶段记录模板

```md
# Phase NN 阶段名称

- 状态：active / archived
- 范围：本阶段交付什么
- 归档判据：本阶段满足哪些条件才能归档

## 1. 目标与范围
本阶段要交付的行为、接口或产物，以及明确不做的内容。

## 2. 输入与决策
需求来源、关键假设、相关 ADR、外部依赖。

## 3. 完成条件
可验证的功能、迁移、契约、测试与文档条件（逐项列出，便于打勾）。

## 4. 实际变更
完成后填写真实实现与受影响的组件。

## 5. 验证记录
逐项记录**实际执行的命令、环境与结果**；未执行项必须写明原因。
禁止使用"应该通过""理论上可用"。

## 6. 风险与遗留项
只写真实未解决的问题，附责任方与下一阶段入口。

## 7. 文档影响检查
列出本阶段更新的需求/架构/API/数据库/测试/运行手册；无影响时明确写明"无"。

## 8. 下一步
下一阶段的入口动作。
```

## 归档门禁

只有**同时**满足以下条件，才能把阶段文件从 `active/` 移到 `archive/`：

1. 阶段完成条件**全部**满足。
2. 代码自查、静态检查、类型检查、必要测试与构建**真实通过**。
3. API、数据库、架构、测试、README、运行手册**已经同步**。
4. **没有被隐藏、吞并或降级处理的失败**。
5. 遗留风险已明确记录，且**不构成该阶段完成条件的一部分**。
6. 契约版本与四份锁一致；需求编号基线完整。
7. 没有 mock 交付残留、未实现业务路由或占位响应。

**不满足时**：阶段保持在 `active/`，写明已确认事实、阻塞原因、恢复验证所需操作。

> **不得仅因为"代码写完了"就归档。** 归档的含义是"这些能力已被验证"，不是"这些代码已存在"。

## 归档动作

1. 移动文件到 `archive/`。
2. 更新 `archive/README.md` 索引：阶段名、结论、完成日期、后续阶段链接。
3. 归档文件**原则上不再改写**；若需纠正历史事实，保留修订说明，不要静默重写结论。
