# CHG-0022 标签形态的声明缺口：两处输出字段没有写出系统实际保证的约束

- **级别**：P2 语义（补上遗漏的约束；不改任何字段的含义、必填性或类型）
- **状态**：已生效（契约）；B3 **无代码改动**（实现已经是对的，契约只是把已成立的事实写出来）
- **契约版本**：0.14.0 → **0.15.0**
- **依据**：`RQ-B-3-20`；`CHG-0008`（`tags` 写路径）；B1 在实现覆盖度视图时按规程上报

## 1. 问题：同一个值集在契约里有四种写法，其中两种什么都没说

契约对"标签"这个值集的声明**四份不一致**（`contracts/openapi/b3.yaml`）：

| 位置 | 声明 | `pattern` | 长度 |
|---|---|---|---|
| `listQuestions` 的 `tags` **查询参数**（`:46`） | `minLength: 1, maxLength: 40, pattern: '^[a-z0-9][a-z0-9-]*$'` | ✅ | ✅ 1–40 |
| `QuestionDraftInput.tags[]`（**输入**，`:954`） | 同上 | ✅ | ✅ 1–40 |
| `QuestionTagCoverage.tags[].tag`（**输出**，`:787`） | `minLength: 1, maxLength: 40` | ❌ | ✅ 1–40 |
| `QuestionPublic.tags[]`（**输出**，`:822`） | `{type: string}` | ❌ | ❌ **无** |

后果是可观察的：B1 在实现覆盖度视图时无法判断端点返回的 `tag` 能不能直接当筛选取值用。
它的处置是**防御性**的——原样渲染计数，只在"归一化后与原值相同"时才给筛选入口，并为此写了一段
文案解释。那段分支**按其自身逻辑永远不会触发**（见 §2），但它之所以存在，是因为**契约没有说**。

## 2. 判定：`pattern` 是系统实际保证的事实，不是偏好

判定依据不是"写上更好看"，而是**写入路径与读取路径都强制它**，逐处可查
（`B3/src/autograder_b3/domain/tags.py`）：

| 证据 | 位置 | 内容 |
|---|---|---|
| 写入时**拒绝**而非改写 | `:10-12`、`:50-56` | "Invalid input is rejected with `422` **rather than rewritten**: a tag the caller did not ask for would make every tag-derived view quietly wrong"。`_TAG_RE.match(tag)` 不匹配即拒 |
| 读取时**再次校验** | `:64-75` | `tags_from_storage()` 对从 `jsonb` 读回的值重新走同一校验，并"refusing anything the validator never wrote"；畸形值报为缺陷（响亮的 `500`），**不会**被传进公开响应 |
| 上限 40 / 每题 20 | `:24`、`:42` | 与契约声明的边界同源 |

因此：**本系统能产出的每一个标签都匹配 `^[a-z0-9][a-z0-9-]*$` 且长度为 1–40。**
输出声明里缺这两项，是**契约少写了**，不是"实现更严格"。

> 注意这里与 `CHG-0017` 的区别：那条是**契约与实现相反**（契约说可选、实现说必填），要改实现。
> 这条是**契约比实现少写**，实现已经是对的，只需把已经成立的事实写出来。两者都是"契约不完备"，
> 但**修哪一边完全相反**，不能套同一个处置。

## 3. 变更内容

`contracts/openapi/b3.yaml`，两处**只补约束、不改类型**：

```yaml
# :787  QuestionTagCoverage.tags[].tag
tag: {type: string, minLength: 1, maxLength: 40, pattern: '^[a-z0-9][a-z0-9-]*$'}

# :822  QuestionPublic.tags[]
tags:
  type: array
  maxItems: 20
  items: {type: string, minLength: 1, maxLength: 40, pattern: '^[a-z0-9][a-z0-9-]*$'}
```

`QuestionPublic.tags[]` 同时补 `maxItems: 20`：契约在 `QuestionDraftInput.tags` 与
`listQuestions.tags` 两处都声明了每题最多 20 个标签，而写入路径按 `MAX_TAGS` 拒绝第 21 个
（`tags.py:42`），所以"最多 20"同样是一个已经成立的事实。

**不改** `QuestionDraftInput.tags[]` 与 `listQuestions.tags`（它们已经是完整的）。
**不新增** 受控词表——`tags.py:4-8` 明确记录了"没有受控词表、没有同义词映射、没有自动更正"这个
决定及其理由（`"进程调度"`、`text-tools` 这类合法主题名不该被静默拒绝），本 CHG **不动**那个决定。

无新字段、无新端点。补上 `pattern` 只会让一份**更严格**的校验在客户端可用。标签不是敏感数据。

按 `change-protocol.md` 第 14 行，P2 在"不破坏兼容"时可选 PATCH；本项目此前对同类

不单独制造一次版本跃迁。

## 9. 验证（实施后执行，未完成前不得声称已通过）

1. 用契约 schema 校验真实端点的一条**非空**覆盖度响应：必须通过。
2. **反向**：构造一条 `tag` 为 `"Process Scheduling"`（含空格与大写）的响应，用**契约校验器**必须
   被拒。这一条是"这次补的约束真的会起作用"的证明——只证明合法值通过，等于没证明约束存在。
3. 写入路径的行为**不变**：`POST/PATCH` 带 `"Process Scheduling"` 仍返回 `422`
   （`tags.py:50`），且错误文案仍说明"declared form"。
4. `QuestionPublic.tags[]` 补上 `maxItems: 20` 后，用真实 `GET /api/v1/questions` 的响应校验通过。
5. `check_shared_vocabularies()` 保持通过（本 CHG **不**新增重复词表——`pattern` 是内联字面量，
   与 `CHG-0019` 的 `failure_category` 不是一回事）。

> 第 2 条依赖能把"非空标签"写进真实题库，而那被 `CHG-0017` 的缺失实现挡住（`phase-02` §3.15 B）。
> 因此本 CHG 的验证项 1、2 与 `CHG-0017` 的落地**有先后依赖**：`CHG-0017` 先落地，才能造出非空标签。
