# CHG-0002 inbox 去重表的主键口径：`event_id` 单列 vs `(consumer, event_id)` 复合

- 级别：**P4（文档）**——只涉及 `MAIN/docs/api/events.md` §5 清单的措辞；`contracts/**` 不含 inbox 表结构
  （表结构以各模块迁移为准）。
- 提出人 / 日期：B2 / 2026-09-16
- 状态：**已生效（判定：采纳复合键，改条文）** / 判定日期 2026-09-18
- **契约版本**：0.1.0（未改契约：判定为改条文）

## 动机

`MAIN/docs/api/events.md` §5（消费者实现清单）第 2 条写："inbox 表以 `event_id` 为主键，插入冲突即视为
已处理（幂等）"。B2 的实现把 `b2.inbox_events` 的主键建为 **`(consumer, event_id)` 复合键**
（`src/autograder_b2/db/schema.py`，迁移 `20260915_0002_*`）。

按 [change-protocol.md](../change-protocol.md) 的"常见场景速查"：发现契约与实现不一致时**不**顺着实现改
契约、也**不**偷偷改实现对齐，而是提 CHG 由 MAIN 判定。

## 已确认事实（独立复核者实测，非实现者自证）

- 真实目录：`b2.inbox_events` 的 PK = `['consumer', 'event_id']`。
- 语义差异是**真实存在**的，不只是措辞：
  | 情形 | 单列 PK（§5 字面） | 复合 PK（现实现） |
  |---|---|---|
  | 同一消费者重复收到同一 `event_id` | 冲突 ⇒ 已处理（正确） | 冲突 ⇒ 已处理（一致） |
  | 消费者 A、B 各自订阅同一事件 | **B 被判"已处理" ⇒ 静默漏处理** | 各自独立去重（正确） |
  复核者用两个消费者处理同一 `event_id` 实测：复合键下 `duplicate=False, handled=True`；若按单列键，
  这一行会因 A 已插入而被判成重复，B 的业务效果永不发生。
- B2 当前只订阅 1 个 subject、只有 1 个消费者，故**今天的差异不可达**；差异在"B2 增加第二个消费者"
  时立刻变成静默漏处理（无日志、无告警），属"未来可达的错误"，不是纯风格问题。

文档应写明"多消费者时必须按 `(consumer, event_id)` 去重"。

## MAIN 判定（2026-09-18）：**采纳 —— 改条文为 `(consumer, event_id)` 复合键**

**理由。** 单列键在多消费者场景下不是"更严格的去重"，而是**静默漏处理**：消费者 A 订阅并处理了事件
`E` 之后，消费者 B 收到同一个 `E` 时会被判成"已处理"，于是 B 的业务效果永不发生，且没有日志、没有
告警、没有 DLQ——这类错误的可见度为零。复核者用两个消费者对同一 `event_id` 实测复现了这个反例。
复合键在单消费者时与单列键**完全等价**，在多消费者时是唯一正确的语义，因此没有理由保留单列键的
措辞。

**已实施的改动（文档，两处）。**

- `MAIN/docs/api/events.md` §2「核心约定」表：`消费` 一行改为
  "**inbox**：以 `(consumer, event_id)` 为唯一键去重（每个消费者各自去重）"。
- `MAIN/docs/api/events.md` §5「消费者的实现清单」第 2 条改为复合键，并附一段说明为什么不是单列键
  （引用本 CHG）。

**契约文件改动：无。** `contracts/**` 不含 inbox 表结构（表结构以各模块迁移为准），摘要未因本项变化。

**模块侧：无代码改动。** B2 的 `b2.inbox_events` 主键早已是 `(consumer, event_id)`——本项只是让文档
追上实现。B3 的 `b3.event_inbox` 与 B4 的 `b4.inbox_events` 由各自迁移定义，在只有单消费者时与
复合键等价；若将来增加第二个消费者，**必须**按复合键实现，这一条现已写进清单。
