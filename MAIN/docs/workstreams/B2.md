# B2 工作包说明（Workstream Brief）

> 本文件是 MAIN 对 B2 的**任务书**。B2 团队（2～3 人）据此拆分认领；B2 自己的 `docs/collaboration/workpackages.md` 必须与本文件一致。

- 责任需求：`RQ-B-2-10`～`RQ-B-2-80`、`RQ-B-2-99`（共 9 条）
- 需求权威：`MAIN/docs/requirements/rq-catalog.md` 第 3 节
- 契约权威：`MAIN/contracts/openapi/b2.yaml`、`MAIN/contracts/schemas/submission-envelope.schema.json`、`evaluation-package.schema.json`、`evaluation-report.schema.json`、`MAIN/contracts/asyncapi/events.yaml`
- 本模块文档规范：`MAIN/docs/collaboration/module-doc-spec.md`

---

## 1. 唯一职责

接收（API / IMAP）待测代码 → 存储管理 → 静态合法性检查 → 安全性确认 → nsjail 动态执行 → 生成可解释、可重放的逐项证据 → 成绩与报告持久化 → 按格式导出。

B2 是整个系统中**分数与执行证据的唯一权威**。

## 2. 边界（越界即缺陷）

| 类别 | 内容 |
|---|---|
| **我拥有** | `b2` schema：submission、artifact、evaluation run/result、security finding、email checkpoint；评测证据与分数；成绩导出 |
| **我不拥有** | 题目、参考答案、测试用例（B3）；身份、课程、选课（B4）；UI（B1） |
| **我禁止** | 读取 `b3`/`b4` schema；导入 B3/B4 的 ORM 或 Python 包；执行用户提供的 shell 字符串；把源码/答案/隐藏用例写入日志、事件、导出；把静态检查未通过伪装为"运行成功"；用 mock 评测充当交付 |
| **我禁止（安全）** | 以 root 运行待测代码；允许网络访问；可写根文件系统；不清理超时进程树；无资源上限执行 |

## 3. 逐条需求落点

| RQ | 实现落点 | 关键契约 | 验收要点（摘要） |
|---|---|---|---|
| `RQ-B-2-10` | FastAPI 提交端点 + 信封校验 | `submission-envelope.schema.json` | Schema 校验、摘要核对、幂等、作用域 403、大小上限、事件不含源码 |
| `RQ-B-2-20` | IMAP adapter → 同一 `SubmissionEnvelope` | 应用内部模型 | 唯一匹配失败则隔离不评分；检查点幂等；重复投递不重复提交 |
| `RQ-B-2-30` | 内容寻址存储 + 元数据 | `b2` schema | 按 SHA-256 去重；服务端生成路径；读权限；孤儿内容可回收 |
| `RQ-B-2-40` | 静态检查器（Python AST / `bash -n` / 结构化规则） | `evaluation-report` 的静态段 | 逐条规则含 severity+位置；**高危阻断动态运行**并置 `rejected` |
| `RQ-B-2-50` | nsjail runner + 逐用例比较 | `evaluation-package.schema.json` | 逐用例证据；超时清进程树；资源限制强制；重复评测同分 |
| `RQ-B-2-60` | 运行/结果持久化 + 导出 | `b2` schema | 绑定摘要完整；状态迁移史；导出防注入且不含源码 |
| `RQ-B-2-70` | 安全判定（静态高危 + 沙箱违规） | `b2` schema security_finding | 禁网可验证；`rejected` 区分于 `failed`；"未检查"≠"安全" |
| `RQ-B-2-80` | 报告生成（总评 + 细评） | `evaluation-report.schema.json` | 每分可追溯；合计校验成立；可重放；学生视图脱敏 |
| `RQ-B-2-99` | 结构化日志 + 关联 ID | 无 | 脱敏；全链路 `correlation_id` 可串；异常路径有日志 |

## 5. 工作包拆分（4 条泳道）

> 前三条对应需求基线里的 9 条 `RQ-B-2-*`；**第四条对应团队自选增量 `RQ-T-20` / `RQ-T-30`**，
> 它们是本项目在基线之外自己加的能力，因此不在 `checks.py` 的 32 条 `RQ-B-*` 基线与
> `check_requirement_baseline()` 的覆盖范围内（那 32 条必须一条不差，而 `RQ-T-*` 由
> `checks.py` 的 `team_expected` 单独登记）。**B2 的追踪表此前引用了 `WP-B2-D` 而本文件没有定义它**
> ——工作包编号是 MAIN 的权威，因此由 MAIN 在此补上定义，而不是让模块自己去发明编号或删掉引用。

### WP-B2-A 接收与存储（`RQ-B-2-10`、`RQ-B-2-20`、`RQ-B-2-30`）

- 产出：提交 HTTP 端点与信封校验、内容寻址存储层、元数据表、IMAP 收取适配器、隔离区、检查点。
- 依赖：MAIN `submission-envelope` schema；B4 JWT 校验（**可先用契约夹具与本地测试密钥**）。
- 验收：三条 RQ 的全部验收项。
- 风险：邮件来源不可控 → 隔离机制必须先于自动匹配实现。

### WP-B2-B 静态合法性与安全性（`RQ-B-2-40`、`RQ-B-2-70`）

- 产出：Python AST 检查器、Bash 语法/结构化检查、规则目录（规则 ID + severity + 说明）、安全规则集、`security_finding` 持久化、静态→动态的阻断门。
- 依赖：`evaluation-package` 中声明的语言与检查策略；MAIN 的语言枚举（`RQ-B-0-10`）。
- 验收：2-40 的 5 条 + 2-70 的 5 条，含恶意样本回归集。
- 风险：静态检查在沙箱内执行、且不得 import 待测模块 → 必须先定好执行策略，否则会踩到副作用。

### WP-B2-C 动态执行与评价输出（`RQ-B-2-50`、`RQ-B-2-60`、`RQ-B-2-80`、`RQ-B-2-99`）

- 产出：nsjail 策略（参数数组）、三种 adapter 的执行器对接、结果比较器、资源限制与进程树清理、证据与报告生成、数据库持久化、导出、结构化日志。
- 依赖：B3 evaluation package 结构与三类 adapter manifest（**这是 B2 最关键的跨模块依赖**）。
- 验收：2-50 的 6 条 + 2-60 的 5 条 + 2-80 的 5 条 + 2-99 的 4 条。
- 风险：nsjail 只能在 Linux 验收；Windows 上必须先有"可测的比较器与报告"作为可交付部分，不得整体阻塞。

### WP-B2-D 教学评语轨与评分参考（`RQ-T-20`、`RQ-T-30`）

- 产出：评语生成的编排（provider 适配、prompt 版本化、显式免责标注）、`advisory_score` 的**严格解析**
  与边界判定、四列存储与三条表级 CHECK、`GET`/`POST /api/v1/evaluation-runs/{id}/commentary` 的对外出口。
- 依赖：`CHG-0011`（评语轨的对外接口）、`CHG-0018`（评分参考）、`ADR-0009`（AI 边界）与 `ADR-0014`
  （双轨与评分参考的六项可执行分离断言）；外部 provider 由 Doppler 配置，**默认关闭时不得出网**。
- 验收：`CHG-0018` §7 的五条 + `CHG-0011` 的实现侧断言。
  **其中两条是否定断言，价值最高**：① 参考分**不得**出现在报告、成绩、导出、任何事件或 `result_digest` 的
  任何位置（它是子对象 `commentary.advisory_score`，访问路径本身就在说"它不是分"）；
  ② 删掉评语行之后**重放**，分数与 `result_digest` 逐字不变——参考分必须是纯附加的。
- 风险：**模型输出非确定**，越界、畸形、模型自带 `max_score` 这些路径**无法靠真实模型稳定触发**，
  只能用传输替身覆盖。因此必须如实区分"真实 provider 跑过的"与"只在替身下验证的"，不得混同。
  另有一条环境级限制：Windows 上沙箱不可用 ⇒ 没有 `completed` 运行 ⇒ 没有 `case_evidence` ⇒
  **真实 `advisory_score` 无法在集成环境产生**（`max_score` 由证据权重和填入，无证据即无从填）。
  该结论有实测支撑，见 `phase-02 §3.15`；**不得**为了演示而伪造一条 completed 运行。

## 6. 并行前提与串行点

- **可并行**：四条泳道共享的只有 `b2` schema 迁移文件与 package 内部接口；A/B/D 可完全并行
  （D 只读运行与证据，不写 A/B/C 的表），C 依赖 B 产出的"阻断判定"接口签名（先冻结函数签名即可并行）。
- **必须串行**：
  1. `b2` schema 的初始迁移（一人先建，其他人基于它加表）。
  2. runner 内部接口签名（`run_case(package, submission) -> CaseEvidence`）——冻结后才允许四条泳道并行。
  3. 报告的最终结构（受 `evaluation-report` schema 约束，不可自行改）。
  4. 契约变更（走 MAIN 变更规程）。
  5. 事件发布的 outbox 实现（共享，一人实现）。
- **共享文件冲突预防**：`plugin.py`、`alembic/`、错误码目录为共享文件；`plugin.py` 的 descriptor 变更只能由一人执行并同步 `module.yaml`。

## 7. 完成条件（Workstream DoD）

1. 9 条 `RQ-B-2-*` 全部为 `已完成` 且可追溯到真实测试。
   `RQ-T-20` / `RQ-T-30` 是基线之外的自选增量，**不计入这 9 条**，但同样必须"状态与证据一致"；
   它们与 `WP-B2-D` 的对应关系记录在 `B2/docs/requirements/traceability.md`。
2. `uv run ruff check .`、类型检查、`uv run pytest` 通过。
3. `b2` 迁移可在空库上从零执行并达到与 `module.yaml: database.migration_head` 一致的 head。
4. Linux 环境下完成一次真实 end-to-end 评测（含 nsjail、禁网、资源限制）并记录命令与结果。
5. 资源实测：单并发评测 RSS ≤96 MB、CPU ≤0.45 核（记录测量方法）。
6. 存在"恶意样本被阻断"的回归证据，且证据来自真实执行而非断言。
7. 无 mock 评测残留；无跨 schema 访问；无 shell 字符串执行。
8. 冷启动验收通过。

## 8. 不可修改的公共契约

- `MAIN/contracts/**` 内容（B2 提供者身份但仍不得单方修改；变更走规程）。
- 提交状态机取值集合：`received → validated → queued → running → completed | rejected | failed`。
- 事件 subject 命名与 envelope 结构；事件不得携带源码/答案/隐藏用例/PII。
- ID 与时间规则：UUID v4、UTC RFC 3339。
- 错误格式 RFC 9457 + `traceparent` / `X-Request-ID`。
- 资源账本：单并发 nsjail 作业 ≤96 MB / 0.45 vCPU；初始只允许 1 个动态评测并发。

## 9. 已知风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| nsjail 仅 Linux 可用 | 动态评测无法在 Windows 验证 | 把比较器、报告、持久化做成平台无关部分先行交付；Linux 验收单独排期 |
| B3 package 结构变更 | runner 核心返工 | package schema 已锁定；变更必须走 MAIN 规程并升版本 |
| `descriptor.events` 为扁平元组，与 `module.yaml` 的 publishes/subscribes 不一致 | 无法校验事件声明一致性 | 记录为已知缺口，在阶段文档与 ADR 中明确，待 SDK 演进 |
| IMAP 外部服务不可控 | 接收链不可复现 | 用本地 IMAP 夹具测试解析与幂等；真实邮箱验收单独记录 |
| 超时进程树清理 | 资源泄漏、后续评测受污染 | 必须有专门的清理测试与残留进程检查 |
