# ADR 0006 事件驱动解耦：at-least-once + outbox/inbox + DLQ

- **状态**：接受
- **背景**：

  模块间存在必须解耦的异步关系：

  - B2 评测完成 → B3 需要据此生成题目统计（`RQ-B-3-30`），但 **B3 绝不能读学生源码**；
  - B3 发布题目版本 → B2 需要感知可用性变化；
  - B4 名单导入完成 → 其他模块可能需要感知；
  - B1 需要实时进度（`RQ-B-1-50`），但进度是"推给一个浏览器会话"而非"广播给系统"。

  如果这些关系用同步 HTTP 实现：

  - B3 统计会让 B2 依赖 B3 的可用性（或反之），破坏"即插即用"；
  - 设计期统计与评测期执行耦合在同一请求里，一次评测的延迟被统计逻辑拖累；
  - 隐私边界会退化为"代码约定"（因为同步调用便于顺手传源码），而不是结构性保证。

  可选方案：

  | 方案 | 解耦 | 隐私边界 | 可靠性 | 资源开销 | 结论 |
  |---|---|---|---|---|---|
  | A. 全部同步 HTTP 调用 | 低 | 靠约定，易破 | 请求失败即业务失败 | 低 | 否 |
  | B. 数据库轮询（对方查表） | **无**（需要跨 schema 访问） | 破坏 | 一般 | 低 | 否（违反 ADR-0001） |
  | C. **消息中间件 + 事件** | 高 | **结构性保证**（payload 可审计） | at-least-once + 重试 + DLQ | 中（NATS ≈32 MB） | **采纳** |
  | D. Kafka / RabbitMQ | 高 | 同 C | 同 C | **高**（JVM/Erlang 常驻内存远超预算） | 否（资源账本不允许） |
  | E. Redis Streams | 高 | 同 C | 一般（持久化与消费者组语义弱于 JetStream） | 低 | 备选，未采纳 |

- **决策**：

  1. **唯一消息中间件为 NATS JetStream**（`RQ-B-4-20`，B4 负责运行维护）。选它的理由是：单二进制、常驻内存小（≤32 MB）、原生支持 JetStream 持久化与 durable consumer，符合资源账本。
  2. **主题命名固定**：`autograder.v1.<domain>.<event>`；权威清单在 `MAIN/contracts/asyncapi/events.yaml`。
  3. **统一信封**（`event-envelope.schema.json`）：`event_id`、`event_type`、`schema_version`、`occurred_at`、`correlation_id`、`causation_id`、`producer`、`payload`。
  4. **投递语义为 at-least-once**，因此**每个消费者必须幂等**：
     - 消费者实现 **inbox**（以 `event_id` 为主键的唯一表）；
     - 重复投递时跳过业务处理，但可以安全地重放副作用。
  5. **发布方实现 outbox**：事件与业务数据变更在**同一数据库事务**中写入 outbox 表，再由投递器异步发出。避免"业务提交成功但事件丢失"。
  6. **重试与死信**：超过最大投递次数的消息进入 **DLQ**，可查询、可人工重放；不允许静默丢弃。
  7. **隐私由 payload 结构强制**：事件 payload **不得**包含源码、参考答案、隐藏测试用例、expected output、凭据、超范围 PII。统计所需的字段只允许是**去标识化**的聚合输入（如 `evaluation_run_id`、`question_version_id`、通过/失败、失败类别、分数）。**B3 无法通过事件拿到源码——这是设计出来的，而不是约定出来的。**
  8. **同步与异步的分工明确**：
     - **同步**（HTTP）：用户直接等待结果的交互（提交接收、查询、导出、SSE 进度流）。
     - **异步**（事件）：模块间的状态传播与派生（统计、缓存失效、审计传播）。
     - 用户可见的实时进度用 **SSE**（面向单个浏览器会话），**不**通过广播事件实现——避免把会话级数据放进系统级事件流。
  9. **中间件不可用时的行为统一定义**（避免各模块各自发明降级逻辑）：
     - 同步 HTTP 路径**继续工作**（提交仍可被接收并落库）；
     - 待发事件留在 outbox，投递器恢复后补发；
     - readiness 反映真实状态（NATS 不可用则 readiness 失败并指明 `nats`）；
     - **不允许**因事件不可用而回退为"删除事件"或"同步直接调用对方"。

- **后果**：

  - **获得**：B2 与 B3 之间没有任何同步依赖，各自可独立部署、独立宕机恢复。
  - **获得**：隐私边界成为**结构性**的——B3 的统计输入在类型上就不包含源码字段。
  - **获得**：评测完成与统计生成解耦，评测延迟不受统计逻辑影响。
  - **付出**：必须实现 outbox/inbox 与去重逻辑（每个生产者与消费者都有一定样板成本）。
  - **付出**：调试变复杂——一条业务链路跨进程且异步，需要 `correlation_id` 才能串起来。这是 `../api/identifiers.md` 第 5 节强制关联 ID 的原因。
  - **付出**：引入了"最终一致性"——统计数值可能短暂落后于评测完成。需要在 UI 上如实呈现（统计是"截至某时刻"），不能假装实时。
  - **遗留风险**：
    - 如果 event payload 日后被加入可识别字段，隐私边界会被侵蚀 → 用"消费端校验 + 契约审查 + 变更规程的安全检查步骤"三重兜底（`../contracts/change-protocol.md` 第 2 步）。
    - 消息积压可能导致统计长期落后 → 需要监控 consumer lag，并记录在 runbook。
    - DLQ 若长期无人处理会累积（占用 JetStream 配额 ≤0.25 GB）→ 需要定期巡查流程。
    - "按需"启用（`RQ-B-4-20` 原文）意味着：若某阶段没有事件消费者，可以不启用 JetStream 而只跑同步路径。这一灵活性**不得**被用来偷偷退化为同步跨模块调用。
