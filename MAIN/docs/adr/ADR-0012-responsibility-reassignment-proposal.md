# ADR-0012 职责归属提案：执行与评分的归属变更（待课程方批准）

- **状态**：**提议**（未生效，**不得据此改代码**）
- **影响范围**：B2、B3、MAIN、B1
- **关联需求**：`RQ-B-2-40/50/70`、`RQ-B-3-10`～`RQ-B-3-60`
- **关联决策**：[ADR-0002](ADR-0002-current-xlsx-requirements-baseline.md)（需求基线）、[ADR-0001](ADR-0001-plugin-composition-and-schema-ownership.md)

---

## 为什么是"提议"而不是"接受"

项目负责人（2026-09-18）要求把**执行与评分**从 B2 挪给 B3。这个变更**不是 MAIN 能单方面决定**的：
模块职责来自课程的 `课程项目需求列表.xlsx`，而 ADR-0002 已裁决 XLSX 是规范基线，
导图与 XLSX 冲突处以 XLSX 为准。XLSX 把"待测代码安全性确认"与"生成答案代码评价结果"划给 **B2**。

因此本 ADR 的定位是：**把变更准备到"课程方点头即可执行"的程度**，并如实说明不批准时的后果。
在获得课程方明确认可之前，本 ADR 不具有约束力，任何模块都不得据此改动实现。

> 项目规则要求"需求归属变更属 P3 级，需要新 ADR + 全模块同步"。本 ADR 是那个 ADR；
> 但 P3 变更的**授权**必须来自需求方，不能来自实现方。

## 背景

### 被评估的方案

| 方案 | 做法 | 结论与原因 |
|---|---|---|
| A. 维持现状（B2 执行与评分，B3 出题与统计） | 不改 | 与 XLSX 一致；已实现并部分验收 |
| B. 全面搬迁：B3 接管沙箱执行与评分 | 把 `b2` 的执行/证据/分数整体迁到 `b3` | **代价极高且与 XLSX 冲突**：需要新 schema 归属、迁移历史合并、B4 的授权重做、evaluation package 的消费方反转、PRD §6 的"判分可信任"论点重写（证据与分数将不再由"执行者"持有） |
| C. **能力拆分**：执行仍归 B2，B3 获得"评分规则与质量把关" | B3 定义并**存证**判据质量，B2 执行判据 | **推荐**。它满足负责人想要的"B3 做强"，且不需要改需求基线。见 ADR-0010/0011 与 B3 的 D 簇工作项 |
| D. 只搬"答案评价"不搬执行 | B3 生成评价结果，B2 只跑沙箱 | **否**。评价结果就是分数，拆开会让"分数由谁负责"变得不可判定；且 ADR-0005 的可解释性要求分数与逐项证据同源 |

### 关键事实（决定 B 是否可行）

1. **XLSX 是评分依据。** 迁移职责后，评审按 XLSX 检查时会看到"B3 做了 B2 的事、B2 没做自己的事"，
   即**两条需求同时判为未完成**。
2. **"判分可信任"依赖执行者与记录者同源。** PRD §6.1 的产品论点是"分数是证据链"；
   把执行留在 B2 而把分数搬到 B3，会让分数与逐用例证据跨模块，可解释性与可重放性都变弱。
3. **沙箱资源归属已定形。** nsjail/cgroup 的运行目录、artifact 根、并发槽都在 B2 的配置与
   compose 里；搬迁等于重做 Linux 验收（见 ADR-0010 的复评）。

## 提案内容（若课程方批准）

1. **需求编号迁移**：`RQ-B-2-40/50/70` 中"执行与评分"部分改挂 B3，B2 保留"提交接收、
   内容寻址存储、导出"。同步三处：`rq-catalog.md`、`traceability.md`、
   `checks.py::check_requirement_baseline()`（项目硬规则：不得出现编号差集）。
2. **数据归属**：新建 `b3` 下的执行与证据表，或整体迁移 `b2.evaluation_*` / `case_evidence` /
   `static_findings` / `security_findings`；`database/ownership.md` 读写矩阵同步。
3. **契约**：`b2.yaml` 的执行相关端点迁到 `b3.yaml`；B1 重新生成类型；CHG 走 P3 流程
   （主版本提升）。
4. **事件**：`evaluation.*` 的生产者从 B2 改为 B3；`module.yaml` 的 `publishes/subscribes` 反转。
5. **验收重做**：Linux 沙箱验收、资源账本实测、确定性与重放用例全部重新绑定到新模块。

**执行顺序**（P3 变更必须一次切换、不留兼容层）：课程方批准 → 新 ADR 状态改"接受" →
契约主版本提升 → 三处需求编号同步 → 数据迁移 → 代码搬迁 → 全模块验证。

## 后果（按"若批准"描述）

**获得**

- B3 成为"题库 + 判据 + 执行 + 评分"的完整评测引擎；负责人想要的"B3 做最强模块"在职责上也成立。
- 分数与逐用例证据回到同一个模块，与 PRD §6.1 的证据链论点一致。

**付出**

- **两条课程需求会短暂同时不满足**（迁移期间），因此**只能在整个批次完成后交付**，不能分批上线。
- 全部 Linux 安全验收与资源实测需要重做；这是本提案最大的成本项。
- B2 缩小为"提交与存储"，它的一项创新（沙箱归因面）随执行迁走。

**遗留风险**

- 若课程方不批准而团队仍执行，交付物与评分依据冲突——这是**不可接受的**，因此本 ADR 保持"提议"。
- 搬迁期间的历史成绩可解释性：已发布成绩绑定的是当时的模块与摘要，迁移后重放会跨模块。
  必须在迁移记录里明确"历史成绩按当时摘要只读保存"。
