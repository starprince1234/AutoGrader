# ADR-0010 沙箱隔离：分层强度 + 可证明性（关闭 ADR-0004 的待确认项）

- **状态**：接受
- **影响范围**：B2、B4、MAIN、B1
- **关联需求**：`RQ-B-2-40/50/70`、`RQ-B-4-10`
- **关联决策**：[ADR-0004](ADR-0004-sandbox-technology-selection.md)（**待确认项由本 ADR 关闭**）、[ADR-0001](ADR-0001-plugin-composition-and-schema-ownership.md)

---

## 背景

ADR-0004 选定 nsjail 并留了一个待确认项："课程方是否要求改用 Firejail/Docker"。
项目负责人（2026-09-18）提出"放开 ADR-0004"，但未给出理由或课程方依据。按规则，
这种改动必须先把备选方案重新评估清楚，而不是换一个名字继续跑。

因此本 ADR 重新评估了全部候选，并把"换技术"这个动作拆成两个真实问题：
**(A) 用哪个机制强制隔离；(B) 怎么证明隔离真的生效。**

### 选型复评（针对本项目的硬约束：1 vCPU / 512 MB RSS / 10 GB 磁盘，PRD §8.5）

| 方案 | 隔离强度 | 资源代价 | 结论与原因 |
|---|---|---|---|
| **nsjail + cgroup v2 + seccomp**（现状） | 命名空间 + cgroup + seccomp 三层；`allow_root=false`、`network=false`、`read_only_root=true` | 单进程级，约几 MB | **采纳**。已在 Linux 容器内实测过非 root/禁网/只读根/进程树清理，并且是**唯一**能塞进 0.25 GB 沙箱预算的选项 |
| Docker / containerd | 同级（同样基于 namespace/cgroup） | **常驻 dockerd/containerd ≈ 100–200 MB RSS** | **否**。512 MB 总账本下无法与 Python 运行时、PostgreSQL 客户端、NATS 共存；且"用一个常驻守护进程来跑一次性作业"本身与本项目的资源取向相反。换它得到的安全强度**并不比 nsjail 高**，只多了一层需要维护的守护进程 |
| Firejail | 依赖 setuid 二进制，同 namespace 模型 | 与 nsjail 相近 | **否**。setuid 扩大了信任面（本项目的安全叙事是"最小特权 + 可枚举"，不是"多一个 setuid 程序"）。ADR-0004 已评估过，本次复评结论不变 |
| gVisor（runsc） | 用户态内核，**强于** namespace 隔离 | 每个沙箱一个 Sentry 进程，几十 MB 起 | **否（本期）**。安全性确实更高，但它是"另一个内核"，需要常驻组件与额外的系统调用兼容层；对"学生交单文件 Python/bash 作业"这一用例，收益与代价不成比例。**记录为将来可选强化**，不是本期 |
| 裸进程 / `--privileged` / 放宽 cgroup | 无 | 最低 | **禁止**。`architecture/security.md` 与 SEC-20 明确不允许降级 |

**结论 (A)：机制维持 nsjail。** 这不是"拒绝改动"，而是复评后**换技术会破坏一条硬需求**
（资源账本），并且换来的隔离强度并不更高。ADR-0004 的待确认项就此关闭：
课程方若日后明确要求 Docker/Firejail，需要连同资源账本一起重新裁决。

**结论 (B)：真正缺的不是更强的机制，而是"隔离生效"这件事此前无法被验证。**
所以本次改动的实质是把隔离从"一句话"变成"可核验的证明"。

---

## 决策

1. **机制不变**：nsjail + cgroup v2 + seccomp，`allow_root=false`、`network=false`、`read_only_root=true`；
   B3 生成的 evaluation package 把这些值固定为 `const`，题目作者无法选择退出（已实现）。
2. **新增沙箱自证（canary）**：提供一个可被运维与验收调用的自证入口，用一组**金丝雀作业**
   （尝试读宿主文件、尝试联网、尝试提权、尝试写只读根、尝试超内存/超进程数）逐一验证
   "应当失败"的确实失败，并输出结构化的逐项结论。语义与安全结论保持同一套三态：
   **发现风险 / 未发现风险 / 未检查**——不允许把"没跑"表述为"安全"。
3. **新增逐用例资源计量**：执行后回读 cgroup 的 `memory.peak`、`cpu.stat`、`pids.peak` 并落进证据，
   使资源账本从**配置值**变成**实测值**。
4. **违规必须升级**：运行期捕获到沙箱违规（seccomp 命中、越权写、联网尝试）时，评测结论为
   `rejected`（安全原因），**不是** `failed`，也**不是**一个分数。这条同时修掉一个真实缺陷：
   此前该升级路径缺失，违规的提交会继续跑到 `completed` 并拿到分数。
5. **`infrastructure_error` 语义收紧**：沙箱本身不可用（例如非 Linux 宿主）与"学生代码违规"
   是两件事，前者是技术失败（不给分、不算学生的问题），后者是安全拒绝。两者的区分要体现在
   状态、事件与 UI 文案上，不能都显示成"评测失败"。

## 后果

**获得**

- 隔离从"设计声称"变成**可执行的验收项**：金丝雀清单跑一遍就能证明非 root、禁网、只读根、
  资源上限确实生效，而且这个证明可以被第三方重复。
- 资源账本有了实测数据，`RQ-B-2-50` 的"资源受限"从配置声明变成证据。
- 五个安全违规场景有了统一、可枚举的处置路径；此前"违规仍给分"是一个真实缺陷。
- 不引入新依赖、不增加常驻进程，资源账本不受影响。

**付出**

- 金丝雀作业必须**只在 Linux 上**才能给出结论；在 Windows 上它只能如实报告"未检查"
  （这正是三态存在的意义，但需要向验收者解释清楚）。
- 逐用例资源计量要在每次执行后多读一次 cgroup，属可接受的常数开销。
- `rejected` 与 `failed` 的区分需要在 B2 报告、事件与 B1 文案三处同时正确，否则又变成"都显示失败"。

**遗留风险**

- 金丝雀证明的是"当前内核 + 当前 nsjail 配置下这些逃逸尝试失败"，**不是**形式化保证；
  内核漏洞、配置漂移、容器运行时差异都不在证明范围内。文档必须这样表述。
- gVisor 类方案被推迟而非否决；若课程方日后要求更强隔离，需连同资源账本重新裁决。
- 本机（Windows）无法执行金丝雀，`RQ-B-2-50` 的 Linux 部分仍然只能在 Linux 容器内验收。
