# ADR-0011 跨模块数据组合：走声明式 API，物理隔离保留

- **状态**：接受
- **影响范围**：B1、B2、B3、B4、MAIN
- **关联需求**：`RQ-B-1-30/60`、`RQ-B-2-80`、`RQ-B-3-30`、`RQ-B-4-50`
- **关联决策**：[ADR-0001](ADR-0001-plugin-composition-and-schema-ownership.md)（**本 ADR 明确维持其物理隔离**）、[ADR-0008](ADR-0008-module-settings-view.md)（同一条原则在配置层的体现）

---

## 背景

项目负责人（2026-09-18）提出"放开 ADR-0001 的跨 schema 强隔离"，同时又明确选择了
**"最小权限保持不动"**。这两条直接冲突：跨 schema 拒绝**就是**最小权限在数据库层的实现，
也是 PRD §6.2 第 2 条创新（"单实例多 schema 的强隔离…跨 schema 外键被物理禁止"）。

冲突不能靠"选一个执行"来解决，因为两个诉求背后其实是**两个不同的目标**：

| 诉求 | 真实目标 |
|---|---|
| "去掉跨 schema 隔离" | 想要**跨模块的数据能组合起来用**（成绩旁边要显示姓名学号、"谁还没交"要能算） |
| "最小权限保持不动" | 想要**一条模块越权拿到别人数据时会被物理拒绝** |

这两个目标并不互斥。让它们互斥的是一种特定的实现方式——"直接连别人的表"。
被评估的方案：

| 方案 | 做法 | 结论与原因 |
|---|---|---|
| A. 保留物理隔离，组合走 API | 每个模块只读自己的 schema；需要别人的数据就问别人的端点 | **采纳**。这正是已经生效的设计：B2 的 `student_number`/`display_name` **永远是 null**，因为它只拥有 `b2`；需要姓名的客户端从 B4 的选课端点拿 |
| B. 加跨 schema 只读视图 | 建一个视图把三张表 join 起来 | **否**。视图属于某个 schema，由某个角色持有，于是"谁有权读"重新变成一个约定问题；而且它把三个模块的迁移耦合成一个发布单元——ADR-0001 要防的正是这个 |
| C. 给每个模块另一个 schema 的 SELECT 授权 | 逐表 grant | **否**。授权会被后来的迁移悄悄扩大；"物理禁止"退化成"靠人记得别 grant"。而且它让模块边界在运行时不可见 |
| D. 允许跨 schema 外键 | 用 FK 表达引用完整性 | **否**。外键会让"删一门课"卡在别的模块的表上，并把两边的迁移顺序锁死 |
| E. **组合读模型**：由消费方按声明式 API 组合，答案在契约里 | B1 用 `student_id` 把名单与成绩连接；关联键写进契约 | **采纳**，与 A 同路。CHG-0007 新增的 `EnrollmentPublic.student_id` 就是这条路的落地：把"能连接"这件事变成契约事实，而不是给 B1 开一个数据库口子 |

---

## 决策

1. **维持 ADR-0001 的物理隔离**：每模块独立 schema + 独立 login role + 独立 Alembic 版本表；
   跨 schema 外键、视图、SQL、ORM 一律禁止，由**数据库权限**拒绝，而非靠约定。
2. **跨模块组合必须走声明式 API**，并且**关联键必须写进契约**。任何"两个模块的数据要一起用"
   的需求，交付物是契约里的一个字段或端点，而不是一个数据库授权。
   - 已落地示例：`EnrollmentPublic.student_id`（CHG-0007）使"名单 × 成绩"的连接成为可能；
   - 反例（明确禁止）：给 B2 读 `b4.enrollments` 的权限来"顺便"补上学生姓名。
3. **所有权不因组合需求而改变**：数据仍归原模块；消费方只读**该模块公开的**表示，
   且这些表示必须经过"无受保护内容"检查（参考答案、隐藏用例、源码永不出现）。
4. **主键即接口**：跨模块引用一律用 UUID + 契约，不使用自然键（学号、邮箱），
   因为自然键会变、会重复、会泄漏。
5. **门禁化**：新增一条集成检查，断言 `B*/src` 中不存在对其它模块 schema 的直连
   （跨模块 import 已是通过项，这条补上数据库维度）。

---

## 后果

**获得**

- 两个目标同时满足：数据能组合（`student_id` 让"谁还没交"可做），越权仍被**物理**拒绝
  （实测：`autograder_b4` 角色执行 `SELECT count(*) FROM b2.users` →
  `ERROR: permission denied for schema b2`）。
- 模块边界在运行时**可见且可验证**：不用读代码就知道"谁只能看自己的表"。
- 组合逻辑集中在消费方，因此新增一种组合视图不需要改任何模块的授权或迁移。
- 契约成为"哪些数据可以跨模块使用"的唯一答案，与 ADR-0003 的权威切分一致。

**付出**

- 组合需要多次 API 调用（B1 要分别取名单与成绩再连接），比一条 SQL 慢。
  对课程规模（一个班几十到几百人）可接受；这也是 `Limit` 上限与游标分页必须做对的原因
  ——分页没做对会让"全量连接"拿到残缺数据，从而把"未提交"算错。
- 每个新的组合需求都可能需要一次契约变更（例如 CHG-0007）。这是有意的成本：
  它把"我们打算跨模块用这个字段"变成需要评审的显式决定。
- B1 必须处理"关联键为空"的情况（`student_id` 可空），不能假设两端总能连上。

**遗留风险**

- **超范围 PII 的二次暴露面**：组合视图是新的泄漏面。缓解：组合只允许使用公开 DTO 字段，
  且这些字段本身已按"最小必要"设计；但"成绩 + 姓名的表格"天然比"只有成绩"敏感，
  导出与权限判定必须按最严的那个模块执行。
- 多次调用的**一致性**没有快照保证：两次请求之间名单可能变化。对"谁还没交"这类视图，
  必须把"取数时间"显示给教师，而不是暗示它是一个事务快照。
