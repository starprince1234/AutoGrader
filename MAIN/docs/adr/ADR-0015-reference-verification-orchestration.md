# ADR-0015 参考解答验证的编排归属：B2 执行、B3 记录、教师一键触发

- **状态**：接受（2026-09-20）
- **影响范围**：B2、B3、B1、MAIN（契约）
- **关联需求**：`RQ-B-3-10/20`（题目完整性、发布门禁）、`RQ-T-10`（出题工作流）
- **关联决策**：[ADR-0001](ADR-0001-plugin-composition-and-schema-ownership.md)（数据所有权）、[ADR-0009](ADR-0009-ai-assistance-two-track.md)（出题辅助）、[ADR-0011](ADR-0011-cross-module-composition-via-api.md)（跨模块走声明式 API）
- **解决**：`CHG-0008` 引入发布存证门禁后留下的 UI 死结

---

## 背景

`CHG-0008` 要求：`publish` 一个题目版本前，必须存在一份与 `content_digest` 绑定的
**参考解答验证存证**。这条门禁是**真的**（B3 侧交叉核对摘要，无跳过开关）。

它的设计前提是**执行者 ≠ 记录者**：B3 禁止执行任何东西，跑参考答案的是能执行代码的组件。
当时唯一的执行者是 `MAIN/scripts/verify_question_bank.py`（一个小工具），它把结果提交给 B3 的
**internal + `serviceToken`** 端点记录存证。

这产生了一个真实后果，B1 已按规程上报且 MAIN 从未裁决：

> **B1 的出题界面无法完成发布。** 它不能自己声明"我验证过了"——那会让存证退化成自我声明；
> 它也不能携带 `serviceToken`——那是服务间凭据，不该进浏览器。

于是教师能在界面上把题目写到草稿，然后**卡在发布这一步**，只能找运维跑脚本。
`phase-01 §11.2` 当时写下了正确方向："若日后要教师自助发布，正确做法是**增加平台侧的验证编排**
（能执行代码的组件跑、B3 记录），而不是让前端自己声明。" 本 ADR 就是那次裁决。

## 被评估的方案

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 维持现状（只能跑脚本） | 教师找运维 | **否**。出题流程在半途断掉；且"谁能发布"变成人的问题而不是系统的问题 |
| B. 让 B1 声明"已验证" | 前端提交一个布尔值 | **否**。存证退化为自我声明，`CHG-0008` 的门禁变成装饰 |
| C. B1 携带 `serviceToken` 调 B3 | 浏览器持有服务凭据 | **否**。服务凭据进入客户端，等于把内部通道公开给任何能读页面的人 |
| D. composition host 新增平台编排端点 | host 收教师令牌 → 调 B2 执行 → 调 B3 记录 | **否（本次不采用）**。可行，但要求 host 拥有一个业务端点，与"MAIN 是微内核、不实现业务"的定位冲突（`ADR-0001`）；且它需要一个新的跨模块调用契约 |
| E. **B2 执行并以自己的服务凭据让 B3 记录** | B2 新增一个端点；教师调它；B2 执行参考答案并用**已有的** `B2_B3_AUTHORIZATION` 通道提交存证 | **是**（本 ADR） |

方案 E 之所以成立，是因为一个已存在的事实：**B2 已经在用服务令牌调 B3**（取 evaluation
package，`B2_B3_BASE_URL` + `B2_B3_AUTHORIZATION`）。记录存证走同一个通道，因此**没有引入任何
新的信任关系、新的凭据或新的跨模块机制**。方案 D 需要发明的东西，方案 E 直接复用。

## 决策

### 1. 新增一个 B2 端点：`POST /api/v1/reference-verifications`

- **鉴权**：教师/助教令牌 **+ 该题目的课程写权限**（与 `publish` 同一套判定）。
- **语义**：给定 `question_version_id`，B2 取该版本的 evaluation package，在沙箱里按题目自己声明的
  适配器与比较策略执行**参考解答**，逐用例比对，返回结论。
- **B2 不做价值判断**：它不回答"这道题好不好"，只回答"按这道题自己声明的策略，参考答案是否通过"。
  这是**执行**职责，与 B2 评测学生提交是同一个能力；题目的质量与结构仍归 B3。
- **不落库**：验证是低频动作，结果由 B3 记录为存证；B2 再存一份是第二个事实源。

### 2. B2 在验证成功后，用**已有的**服务通道把存证交给 B3

调用 B3 的 `POST /api/v1/question-versions/{id}/attestations`（internal + `serviceToken`，
`CHG-0008` 已声明）。**不新增 B3 端点，不改变 B3 的鉴权模型**。

### 3. "执行者 ≠ 记录者"因此**仍然成立**，而且更强

- 记录者（B3）依然不执行任何东西；
- 执行者（B2）依然不定义题目、不判分、不写题库；
- 客户端（B1）依然**没有** `serviceToken`，且它对结果的贡献仍然只是"触发"。

教师按钮的语义因此是"**请求平台验证这道题**"，而不是"我确认这道题是对的"。

### 4. 失败的验证**不产生存证**，且必须能让教师看见原因

逐用例的失败结论返回给调用者（哪些用例没过、失败类别是什么），但**不得**把期望输出或隐藏用例
的输入复述给客户端 —— 教师有权看到自己题目的受保护内容，所以这里不是"学生可见面"的问题，
而是**不得让这个端点成为绕过受保护内容访问控制的旁路**：它返回的是与 `view=teacher` 同级的信息。

### 5. **前置条件**（2026-09-20 补充：本 ADR 的决策 1 漏了一项）

决策 1 写"B2 取该版本的 evaluation package"，**没有写明那个取包端点只服务已发布版本**。
实施后在真实 B3 上验证发现：`getEvaluationPackage` 对**草稿**返回 `409`，而
`recordReferenceAttestation` **只接受草稿**——两者相遇使决策 1 的流程**完全不可执行**，
教师**依旧卡在发布**。

**本 ADR 的决策本身不变**（执行者 ≠ 记录者、复用已有服务通道、失败不产生存证），
它缺的是**一条前置条件**：**被验证的版本是草稿，而草稿也必须能取到它的执行输入。**
该前置条件已由 `CHG-0028` 裁决并排期（让草稿也能取包；`created_at` 用内容时间戳、跳过摘要比对）。

> **这是一处"方案正确、前提未写"的缺陷，而不是"方案错误"。** 它值得记在 ADR 里而不是只记在 CHG 里：
> ADR 的读者会照着决策 1 去实现，而**决策 1 单独看是不可执行的**。
> 教训是：写出一个跨模块的调用链时，**每一步的前置条件都要落在纸面上**，
> 否则链条会在"某一步其实不能用"的地方断掉，而断点只会在真实环境里显现。

## 后果

**获得**

- 出题流程闭环：教师在网上完成"写题 → 验证 → 发布"，不再需要运维介入。
- 零新增凭据、零新增跨模块机制：复用 B2 已有的 B3 服务通道。
- `CHG-0008` 的门禁**未被削弱**：存证仍由 B3 记录、仍与 `content_digest` 绑定、
  仍会因题目内容被编辑而失效。

**付出**

- B2 多一个端点与一条对外调用（它此前只**读** B3，现在也**写** B3）。这是本 ADR 最需要留意的一处：
  B2 的"只读 B3"性质被打破。**边界仍在**——它写的是 `attestations` 这一个资源，且是
  `CHG-0008` 专门为它设计的资源，不是题库内容。
- 验证需要沙箱，因此**在 Windows 上必然返回 `infrastructure_error`**（`ADR-0004` 禁止降级为裸进程）。
  这意味着本机**无法演示**一键发布；界面必须把这种情况显示为"验证需要 Linux 沙箱环境"，
  而不是失败或伪装成功。

**遗留风险**

- **教师可对任意自己有写权限的题目反复触发验证**：每次都要起沙箱。缓解：它受与 `publish`
  相同的课程写权限约束，且单并发沙箱（资源账本决定）天然限流。**未加显式速率限制**，记录为已知限制。
