# ADR-0013 模块数是开放的：任意 N 个模块，而不是恰好 4 个

- **状态**：接受
- **影响范围**：MAIN（contracts / host / gates）、B2、B3、B4、未来模块
- **关联需求**：`RQ-B-4-40`（运行期注册表）、`RQ-B-0-20`（工具链基线）
- **关联决策**：[ADR-0001](ADR-0001-plugin-composition-and-schema-ownership.md)（插件式 composition host）、[ADR-0003](ADR-0003-api-authority-and-runtime-registry.md)（设计期/运行期权威切分）

---

## 背景

项目的头条目标是"各模块只要遵守 MAIN 里的组织规范，即可即插即用"。PRD §8.6 把它写成一条**可测**判据：

> **解耦**：移除任一模块，host 能明确指出缺失能力并失败；**新增一个遵守规范的模块，无需修改 MAIN 代码即可装载**。

集成审计用 9 个合成场景实测了真实的 `_load_modules()`，结论是**装载期确实是结构性强制的**：缺能力、
能力环、重复路由、描述符类型错、清单/描述符漂移、摘要漂移都会响亮失败。但"新增一个模块"这条路
在三个地方被**硬编码封死**，于是那句判据只在"恰好这四个模块"的世界里成立：

| 堵点 | 位置 | 后果 |
|---|---|---|
| 模块名 pattern 是 `^B[1-4]$` | `contracts/manifest.schema.json` | 第五个模块**在契约层就被拒**，无法通过清单校验 |
| 同一 pattern 被复制两份 | `B4/src/autograder_b4/registry.py`、`api/modules.py` | 同上；且三处各写一遍，改一处就会不一致 |
| MAIN 把三个业务模块声明为**硬依赖** | `MAIN/pyproject.toml` → `uv.lock` 的 `source = { directory = "../B2" }` | **没有这三个目录，MAIN 连自己的 venv 都装不出来**。"不改 MAIN 即可装载"在**打包层**不成立 |
| 治理门禁把模块列表写成字面量 | `checks.py` 的 `("B1","B2","B3","B4")`（3 处） | 而契约/路由校验用的是 `glob("B*/module.yaml")`（通用）。于是**新模块会被装载，却逃过治理检查**——比拒绝更糟 |

### 被评估的方案

| 方案 | 做法 | 结论与原因 |
|---|---|---|
| A. 维持"恰好 4 个" | 承认这是四人课程作业的固定结构 | **否**。它让 PRD §8.6 变成一句无法验证的话，也让 ADR-0001 的"插件式"退化为"四块拼图"。而且课程组最容易展示的能力——"新模块接上来就能跑"——恰好被它排除 |
| B. 开放模块数，但保留 MAIN 对业务模块的硬依赖 | 只放宽 pattern | **部分**。装载能过，但打包层仍然耦合：`uv sync` 在没有 `../B2` 的机器上直接失败。判据的一半仍然是假的 |
| C. **开放模块数，并把业务模块从 MAIN 的核心依赖移出** | pattern 放宽 + 治理门禁改为发现式 + 业务模块进可选依赖组 | **采纳**。核心安装不含任何业务模块，集成部署按需装上——这才让"MAIN 不依赖具体模块"成为**可安装验证**的事实 |
| D. 让 MAIN 在运行时动态 `pip install` 模块 | host 自己拉依赖 | **否**。把部署期行为变成运行期副作用，且引入了网络与权限面。部署是部署，运行是运行 |
| E. 为任意模块引入 `AutoGraderModule` 基类框架 | 统一继承 | **否**（审计已否决）。它把四份独立演进变成一次四方协同发布，与 ADR-0001 的解耦立法意图相反 |

---

## 决策

1. **模块名开放**：`^B[0-9]{1,3}$`（`B1`…`B999`）。保持 `B<n>` 这一课程既有约定——它同时是
   `checks.py` 的 `glob("B*/module.yaml")` 发现规则——但不再把 `n` 钉死在 1–4。
   `manifest.schema.json` 的 `database.schema` 相应从枚举 `["none","b2","b3","b4"]` 改为
   pattern `^(none|b[0-9]{1,3})$`。
2. **单一 pattern 来源**：pattern 只在 `contracts/manifest.schema.json` 定义一次。registry 侧
   的实现从契约派生（或至少引用同一常量），不再各写一份。
3. **治理门禁改为发现式**：`checks.py` 中所有 `("B1","B2","B3","B4")` 字面量改为
   `glob("B*/module.yaml")` 的发现结果。**新模块必须同时被装载和被治理**——这才是"遵守规范"
   的完整含义。
4. **打包分层**：`MAIN` 的核心依赖只含 SDK 与运行时（fastapi/pydantic/sqlalchemy/psycopg/nats/uvicorn）；
   业务模块移入可选依赖组，集成部署显式安装。核心安装因此可以在没有任何业务模块的机器上完成，
   而 host 在装载不到模块时**响亮失败**（`missing capability`），这正是 ADR-0001 想要的行为。
5. **同名 entry point 只有一个规则：响亮失败**。当前 host 是"后者胜"（`main.py` 用 dict 推导），
   而 B4 注册表是"前者胜"（`if name not in seen`）——**两处口径相反**，冲突能过启动校验，
   只在管理员读注册表时才被发现。改为：装载期发现同名即抛错，两处不再有各自的口径。
6. **host 校验模块清单**：host 目前完全不读 `module.yaml`，于是"没有清单的第五个模块"能正常装载。
   清单校验必须发生在 host 装载期（B4 不在场时也一样），否则"遵守规范"没有执行者。

## 后果

**获得**

- PRD §8.6 从"声称"变成**可执行判据**：可以真的写一个新模块、不改 MAIN 一行、把它装进来并让它
  被门禁治理。这是整份作业最值得在答辩时演示的一件事。
- 核心安装与业务模块解耦，`MAIN` 可以在没有 B2/B3/B4 源码的机器上完成安装与门禁，这一点可被
  `uv sync` 直接验证，而不是靠读代码推断。
- 消除了"新模块能装载却逃过治理"这条**静默**路径——静默比拒绝危险得多。
- 同名 entry point 从"两种相反的静默取舍"变成一次明确的启动失败。

**付出**

- 集成部署必须显式安装业务模块（可选依赖组）。运行手册与 `run_host.ps1` 需要相应更新，否则
  开发者会遇到"模块不见了"的困惑——这是一次性的文档成本。
- `manifest.schema.json` 是契约的一部分，改它意味着一次契约版本递增与四份 `contracts.lock` 重算。
- 发现式门禁意味着新增模块时，它的文档/编码/端口都会立刻被纳入检查。这会在新模块尚未写完文档时
  产生红灯——这是**有意的**：治理从第一天就生效，而不是等人记得加进去。

**遗留风险**

- **能力名仍是自由字符串**（`b4-auth`、`b3-questions`…），没有集中登记，存在拼写漂移风险。
  发现式门禁不解决这个；`adr/README.md` 的待决策议题已记录。
- **B1 仍不在 capability DAG 内**（ADR-0007 已如实记录）：它的缺失是唯一静默的。
  本 ADR 不放宽也不假装解决这一点——静态客户端与插件不是同一种东西，把它塞进 DAG 需要另一个决定。
- 放宽 pattern 不等于"模块可以随便来"：`module.yaml` 的其余约束（唯一路由、唯一 schema 归属、
  摘要一致、`entry_point` 形状）一条都没放松。
