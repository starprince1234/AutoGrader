# ADR 0004 沙箱执行技术选型：nsjail

- **状态**：接受（含一项**待课程方确认**事项）
- **背景**：

  评测必须执行**学生提交的任意代码**，这是整个系统最大的安全风险面（`RQ-B-2-50`、`RQ-B-2-70`）。需要在 1 vCPU / 512 MB 的预算内做到：禁网、非 root、只读根文件系统、临时工作区、进程/CPU/内存/时间/输出/文件数量限制、超时后清理整个进程树。

  课程材料给出的方向不一致：

  | 材料 | 内容 |
  |---|---|
  | 思维导图（PDF）Beta 子树「开发工具」 | "沙盒：**Firejail, docker** 等" |
  | 需求表（XLSX） | 未规定具体沙箱技术；`RQ-B-0-20` 要求"开发工具、开发语言、目标运行环境符合课程文档" |

  候选方案对比（在 512 MB / 1 vCPU 预算下评估）：

  | 方案 | 隔离强度 | 内存开销 | 启动开销 | 细粒度资源限制 | 结论 |
  |---|---|---|---|---|---|
  | 裸进程 + `resource` 限制 | 极低（无文件系统/网络隔离） | 最低 | 最低 | 部分 | 否（不满足禁网与只读根） |
  | **Docker** 容器 / 作业 | 中高 | **高**：需常驻 dockerd（≈100 MB+），每次评测还需拉/起容器 | 高（数百 ms～秒） | 通过 cgroup 可做，但受 daemon 间接控制 | 否（**内存账本不允许常驻 daemon**） |
  | **Firejail** | 中（依赖 seccomp/namespace 封装） | 低 | 低 | 可做，但参数抽象与 cgroup v2 集成不如 nsjail 直接 | 备选 |
  | **nsjail** | 高（namespace + cgroup v2 + seccomp-bpf 原生） | 低（无 daemon，单进程） | 低（fork+exec） | **原生、声明式、参数数组** | **采纳** |
  | seccomp 自研 + chroot | 需自行实现，易出错 | 低 | 低 | 需自行实现 | 否（自研沙箱是反模式） |

- **决策**：

  1. **采纳 nsjail + cgroup v2 + seccomp** 作为唯一沙箱执行机制。
  2. 沙箱启动**只使用固定参数数组**，绝不拼接 shell 字符串；学生提供的任何内容（文件路径、参数、代码）都不得进入命令行结构位置。
  3. 强制策略：
     - **禁网**（network namespace 隔离，无接口 / 无 DNS）；
     - **非 root**（映射到无特权 uid/gid）；
     - **只读根文件系统**；
     - **临时工作区**（每次评测独立目录，评测后清理）；
     - **限额**：进程数、CPU 时间、内存（≤96 MB）、墙钟时间、stdout/stderr 输出大小、打开文件数、文件大小；
     - **超时清理整个进程树**（防止后台子进程残留并污染后续评测）。
  4. **不可用时不得降级**：若运行环境缺少 cgroup v2 / 非特权用户命名空间，则**拒绝执行动态评测**并报告阻塞——绝不"退化为无沙箱执行"。这是硬规则。
  5. 沙箱策略参数由 B2 拥有并摘要化（runner policy 摘要），作为评测绑定摘要的一部分参与可重放性（见 `../api/identifiers.md` 第 4 节）。
  6. **保留替换可能**：沙箱执行封装在 B2 内部的 runner 接口之后，政策参数与执行机制分离。若课程方要求改用 Firejail/Docker，只需实现新的执行后端，不影响 B3 的 package 契约、评分逻辑与报告结构。

- **待确认事项（需向课程方澄清）**：

  导图写作"Firejail, docker **等**"（"等"表未穷举）。本项目的解读是：课程要求的是"**必须使用沙箱隔离**"这一能力，而非指定某个具体产品；nsjail 满足且更契合资源账本。**若课程方明确要求必须使用 Firejail 或 Docker**，则按 ADR 流程重新评估（预计需要把沙箱作业内存预算上调或调整并发数，因为 Docker 需要常驻 daemon）。

- **后果**：

  - **获得**：在 512 MB 预算内获得高强度隔离，且无需常驻容器守护进程。
  - **获得**：seccomp-bpf 与 cgroup v2 的声明式配置使策略**可被审阅、可被摘要、可被测试**。
  - **付出**：**仅 Linux 可用**（需要 cgroup v2 与非特权用户命名空间）。Windows 上无法验证动态评测能力 → 因此把"比较器、评分逻辑、报告生成、持久化"设计为平台无关部分先交付，Linux 验收单独排期（见 `../runbooks/linux-acceptance.md`）。
  - **付出**：需要在部署环境准备 cgroup v2 配置与必要的内核参数（runbook 覆盖）。
  - **遗留风险**：
    - 容器化部署（Docker Compose）中运行 nsjail 需要额外的权限配置（通常需要 `--privileged` 或特定的 capability/seccomp 放行），这会与"最小权限"原则产生张力 → 需在 Linux 验收时明确记录所选方案与其风险，不得含糊处理。
    - 恶意代码的**资源耗尽型**攻击（如快速 fork）依赖进程数限制与 cgroup 生效；需有专门的回归用例（fork bomb 样本）验证限制真实生效，而不是仅"配置了就算完成"。
    - 沙箱逃逸漏洞是长期风险；本项目不承诺抵抗针对内核 0day 的攻击，但通过禁用网络、只读根与非 root 显著降低影响面。
