# AutoGrader 产品需求文档（PRD）

- 项目代号：**AutoGrader Beta**
- 课程题号：B 题（AutoGrader 作业代码自动评分系统）
- 需求版本：`0.1.0`（契约同步版本）
- 规范性需求来源：`MAIN/课程项目需求列表.xlsx` → 全文见 [rq-catalog.md](rq-catalog.md)

---

## 1. 一句话定位

**面向课程作业的"可解释、可重放"的代码评测平台**：学生提交 Python / Bash 作业，教师维护版本化题库与班级名单，系统返回**逐项可追溯的评测证据**——每一分都能指到具体规则或用例，任何一次评测都能凭摘要重放复核。

## 2. 它解决什么问题

现有课程作业批改的三类真实痛点：

| 痛点 | 现状 | AutoGrader 的应对 |
|---|---|---|
| **判分不可解释** | 学生拿到一个分数，不知道哪一步错了 | 逐规则、逐用例的细节评价；失败可分类（超时/崩溃/输出不符/资源超限） |
| **结果不可复核** | 教师怀疑某次判分，无法复现当时条件 | 绑定五元摘要（提交、题目版本、测试包、runner 策略、执行环境），摘要相同则结果必须相同 |
| **批改不安全** | 直接运行学生代码，可能被盗数据、被挖矿、被拖垮机器 | nsjail + cgroup v2 + seccomp 沙箱，禁网、非 root、只读根、资源硬限制 |
| **流程割裂** | 名单、题目、提交、成绩分散在多个表格与邮箱里 | 统一平台：名单导入、题库、提交、实时进度、成绩查询与导出 |

## 3. 目标用户与角色

| 角色 | 核心诉求 | 主要活动 |
|---|---|---|
| **学生** | 我要知道为什么扣分、能不能再交一次 | 看题目 → 写代码 → 提交 → 看实时进度 → 看逐项反馈与历史成绩 |
| **教师** | 我要把一份名单变成一门课，并把一批作业判完 | 导入/编辑名单 → 建题与发布版本 → 布置作业 → 看班级成绩与题目统计 → 导出 |
| **助教** | 我帮老师改一部分课的作业 | 与教师同权限，但作用域限定在授权课程 |
| **管理员 / 运维** | 我要保证平台活着且没人越权 | 管账号角色 → 查数据库/中间件/模块健康 → 查审计记录 |

> **权限模型**：角色 × 课程作用域。前端可见性只是体验；**判定一律在服务端**（`RQ-B-1-20`）。

## 4. 用户旅程（三条主线）

### 4.1 学生旅程

1. 登录（短期 JWT + HttpOnly 刷新凭据）。
2. 进入课程 → 看到作业列表（assignment）与其题目。
3. 打开题目：富文本题干含文字与**图形**（图片受控加载）。
4. 在代码编辑器中编写答案（Monaco），可本地保存未提交草稿。
5. 提交 → 系统返回 `submission_id`，无需等待。
6. 实时进度：`received → validated → queued → running → …`（SSE 推送）。
7. 评测完成 → 看到**总体评价**与**细节评价**：
   - 静态：哪一行有什么问题（严重级别 + 说明）；
   - 安全：是否触发高危规则（如被拒，说明原因）；
   - 动态：每个用例的输入/实际输出/期望输出/失败类别。
8. 历史成绩：按作业查看历次提交与最好成绩。
9. 若认为判分有误：凭评测 ID 提出复核，教师可依证据链重放。

### 4.2 教师旅程

1. 登录 → 创建课程与课序（section）。
2. 导入名单：上传 PDF/XLSX → 看解析预览 → 必要时手工做**列映射** → 逐行校验结果 → 确认写入（原子提交，未确认前库中零写入）。
3. 编辑名单（需权限，留审计）。
4. 建题：写富文本题干 + 上传图片 + 写参考答案 + 设计测试用例（按 stdin / 文件 / callable 三类之一）。
5. 发布题目版本（**发布后不可变**；要改就出新版本）。
6. 组合作业集合（assignment）并布置给课序。
7. 观察班级成绩：查询、筛选、下钻到单次评测证据。
8. 查看题目统计：作答次数、通过率、失败类型分布 → 反向调整教学。
9. 导出成绩（XLSX/CSV，防公式注入）。

### 4.3 管理员旅程

1. 创建用户、分配角色。
2. 检查数据库、消息中间件、各模块健康（readiness 必须反映真实依赖状态）。
3. 查看模块注册表：装了什么模块、各自契约版本、提供/依赖哪些能力、路由与事件清单。
4. 查询审计记录：谁在什么时候改了什么。
5. 处理名单导入失败、邮件隔离件等运营事项。

## 5. 功能范围

### 5.1 本期范围（32 条课程需求）

- **B1（UI，7 条）**：名单导入与编辑、成绩查询、题目展示（含图形）、答案提交、成绩导出、前端日志。
- **B2（代码管理，9 条）**：API/邮件接收、提交物存储、静态合法性、安全性确认、动态准确性、结果入库与导出、总体+细节评价、日志。
- **B3（题库，7 条）**：题干/参考答案/测试用例、按课程维护题库、答题统计、三类测试框架（stdin / 文件 / 可调用）、日志。
- **B4（平台，6 条）**：数据库运行、消息中间件、表结构规范、模块间 API 运行期注册、用户管理 API、日志。
- **全体（3 条）**：以 Python/Bash 为处理对象、符合课程技术基线、能表达 Unix 作业。

逐条规范解释与验收标准见 [rq-catalog.md](rq-catalog.md)。

### 5.2 明确非目标（本期不做，且不保留半成品路径）

| 非目标 | 说明 |
|---|---|
| C / C++ / Java / 其他语言评测 | 课程只要求 Python 与 Bash；扩展会破坏语言枚举与沙箱策略的简单性 |
| 云端多租户 / SaaS 化 | 单实例课程部署；不做租户隔离与计费 |
| 让模型**替教师决定**题目内容或成绩 | **LLM 不参与判分、不决定成绩**（见下节）。`RQ-T-10` 允许模型按教学目标给出**结构化题目草稿**，但那是教师专用、可编辑、不可直接发布的候选：写入题库、发布版本与判定成绩仍是确定性与人工动作 |
| 生产级高可用（多副本、自动故障转移） | 资源账本（1 vCPU / 512 MB）不允许 |
| 跨区域部署 / CDN | 同上 |
| 移动端原生 App | 仅响应式 Web |
| 学生之间的代码互评 / 论坛 | 无此需求 |
| 旧接口兼容层、双写、灰度开关 | 明确禁止（见 `contracts/change-protocol.md`） |
| 真实邮件服务器搭建 | 用 IMAP 适配器对接既有邮箱；不搭建邮件基础设施 |

## 6. 创新点

产品的差异化不在于"能判分"，而在于**判分可以被信任**。

### 6.1 产品形态创新

1. **成绩即证据链**：分数不是标量，而是"（规则/用例 → 结论 → 证据摘要）"的集合。报告本身是可以被第三方复核的产物。
2. **可重放评测**：绑定五元摘要（提交、题目版本、测试包、runner 策略、执行环境），摘要相同必须同分。申诉复核、教学争议、回归排查都靠它。
3. **静态→安全的阻断语义**：高危代码不进入执行阶段，且状态是 `rejected`（被拒）而**不是** `failed` 或 0 分——语义上区分"你写错了"和"你不该这么写"。
4. **"未检查" ≠ "安全"**：安全结论显式区分三态（发现风险 / 未发现风险 / 未检查），不允许把未检查伪装成安全。
5. **实时评测进度即教学反馈**：SSE 推送阶段进度，让学生看到"机器在做什么"（正在静态检查 / 正在跑第 3 个用例），而非黑箱等待。
6. **题目版本不可变 + 统计闭环**：已发布版本不可改，统计按版本聚合；教师改题不会污染历史成绩的可解释性。
7. **两轨制：可复现的分数 + 可重新生成的教学评语**（2026-09-18 新增，见 [ADR-0009](../adr/ADR-0009-ai-assistance-two-track.md)）：
   分数轨保持完全确定性与可重放；另有一条**独立评语轨**，只从已落库的结构化证据生成教学式解释，
   显式标注"非确定性、不参与判分"，可随时重新生成而不改变任何分数。这样"判分可以被信任"与
   "学生能拿到机器生成的解释"从互斥变成并存——而这是靠**限制评语的输入**（永不读源码）做到的，
   不是靠弱化分数的确定性。

### 6.2 技术栈与架构创新

1. **微内核 + 插件即插即用**：MAIN 是微内核 composition host，B2/B3/B4 是独立 Python 包，通过 Python entry point 装载；按 capability DAG 解析依赖顺序；重复路由、缺失能力、契约摘要漂移都在启动时**明确失败**。
2. **单实例多 schema 的强隔离**：一个 PostgreSQL 承载三个模块，但每个模块有独立 login role + 独立 schema + 独立 Alembic 版本表；**跨 schema 外键被物理禁止**，跨模块引用只能通过 UUID + 契约。
3. **契约摘要门禁**：契约的所有字节参与 SHA-256，四个模块各自持有 `contracts.lock`；任何人偷改契约都会立刻在集成检查中被发现。
4. **测试框架的三型 adapter**：stdin / file / callable 三类题型共用同一 package 结构，**新增题型不需要改 runner 核心**（开放性-封闭性在评测引擎上的落地）。
5. **事件驱动的统计与解耦**：B3 只消费**去标识化**的 `evaluation.completed` 事件做统计，永远看不到学生源码——隐私边界由数据流决定，而不是靠约定。
6. **资源账本驱动的架构**：1 vCPU / 512 MB / 10 GB 的硬预算反向约束了技术选型（NATS 而非 Kafka、单 host 而非多服务、单并发沙箱）。
7. **内容寻址的提交存储**：按 SHA-256 去重，天然支持"同题同代码只存一份"，也让"重放"只需引用摘要。

### 6.3 工程创新

1. **文档即门禁**：需求编号、契约摘要、模块清单都有自动化校验（`host/src/autograder_host/checks.py`），文档漂移会导致检查失败。
2. **四条并行开发线 + 一条串行审批线**：MAIN 契约冻结后 B1/B2/B3/B4 完全并行；只有契约变更串行。
3. **冷启动可验证**：新成员只读三个文件即可跑通门禁并认领需求（见 `collaboration/module-doc-spec.md` 的 onboarding 要求）。

## 7. 关键产品决策（不可协商）

| 决策 | 内容 | 原因 |
|---|---|---|
| **分数完全确定性** | 分数、逐项证据、状态判定不使用任何模型输出；同输入同输出、可重放、每一分可枚举 | 可解释性与可重放性的前提。**2026-09-18 修订**：原条文是"LLM 不参与成绩与反馈"，其中"反馈"部分已由 [ADR-0009](../adr/ADR-0009-ai-assistance-two-track.md) 放开为**独立的评语轨**（只读结构化证据、显式标注、默认关闭）；**分数这一半不变，且是评语轨存在的前提** |
| **模型不接触源码与受保护内容** | 评语只从已落库的结构化证据生成；出题辅助可读教师正在编写的题目，但产物不得把参考答案/隐藏用例复述到学生可见位置 | 保留"受控内容不外泄"这条底线，同时不把学生源码送出系统 |
| **模型服务默认关闭** | 未配置 provider 时系统行为与放开前完全一致，无任何出网调用 | 外部依赖与数据出境必须是显式选择，不是默认行为 |
| **不执行任意 shell 字符串** | 沙箱启动使用固定参数数组 | 命令注入防护的根本手段 |
| **参考答案与隐藏测试永不外泄** | 公开 DTO、事件、日志、学生可见存储中一律不存在 | 学术诚信底线 |
| **安全结论三态** | 发现 / 未发现 / 未检查 | 不允许把未检查表述为安全 |
| **失败要分类** | `rejected`（被拒，安全或静态）≠ `failed`（技术失败）≠ 低分 | 语义清晰，避免把系统故障算成学生的问题 |
| **统计只看去标识化事件** | B3 不读源码 | 隐私边界由架构保证 |
| **无兼容层** | 破坏性变更一次性切换 | 避免双轨导致的隐性缺陷 |

## 8. 成功判据（可观测）

1. **功能**：32 条课程需求全部有可运行实现，且每条都能指向真实测试与阶段证据。
2. **可解释**：任取一次评测，报告中的得分可逐项加总并与总分相等（合计校验成立）。
3. **可重放**：同一提交在同摘要条件下重复评测，分数与逐项证据完全一致。
4. **安全**：恶意样本回归集全部被阻断；沙箱禁网可验证；跨 schema 访问被数据库拒绝；公开响应中不存在受保护字段。
5. **资源**：整套应用 + PostgreSQL + NATS + 一个活动沙箱 ≤1 vCPU / ≤512 MB RSS / ≤10 GB 磁盘（Linux 实测）。
6. **解耦**：移除任一模块，host 能明确指出缺失能力并失败；新增一个遵守规范的模块，无需修改 MAIN 代码即可装载。
7. **可用**：导入 PDF/XLSX 名单 → 发布题目 → 学生提交 → 得到逐项证据 → 导出成绩，全流程无人工数据库干预。
8. **协作**：一个不了解项目的人，只读模块 README + AGENTS.md + onboarding 即可开始认领需求（冷启动验收）。

## 9. 约束与假设

**约束**

- 课程技术基线与目标运行环境（`RQ-B-0-20`）。
- 完整安全与资源验收必须在 **Linux cgroup v2** 环境完成；Windows 仅用于开发与契约检查。
- 无远端仓库、CI、PR 流程（当前阶段）；四个模块各自独立 Git 项目。
- 单并发动态评测（初始）。

**假设**

- 课程作业规模：单班百人以内，单题测试用例数十级。
- 提交物为文本源码文件（Python/Bash），不是二进制或大型数据集。
- 教师具备基本的表格操作能力（列映射步骤需要人工确认）。
- 邮件接收依赖一个可用的 IMAP 邮箱账号（外部依赖，不在本系统内搭建）。

**待确认事项**

- 课程方是否提供固定的 Unix 作业样例集（`RQ-B-0-30` 引用的是外部文档链接）；若提供，将直接转为 B3 的种子题库。
- 邮件接收的实际邮箱与凭据（B2 阶段需要）；在此之前邮件链以本地 IMAP 夹具验证。
