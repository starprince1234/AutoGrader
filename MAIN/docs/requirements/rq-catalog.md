## 1. 全体模块需求

### RQ-B-0-10 以 Python、bash shell 为软件开发和处理的对象

- **原文**：以 Python、bash shell 为软件开发和处理的对象。
- **归属**：全体（B1～B4）。
- **规范解释**：
  - 系统"被评测的作业"只有两类语言目标：Python（3.x）与 Bash shell。
  - 系统自身以 Python 为主体实现语言；B1 前端为 TypeScript/React，但 B1 不构成"处理对象"。
  - 评测对象语言由 B3 的 `adapter` 与 B2 的 runner policy 共同声明，二者必须使用同一枚举。
- **交付物**：
  - `MAIN/contracts/schemas/language.schema.json`（语言枚举：`python`、`bash`）。
  - B3 evaluation package 的 `language` 字段；B2 执行器按语言选择解释器与静态检查器。
- **验收标准**：
  1. 同一道题若声明 `language=python`，B2 必须用 Python 解释器执行且不接受 Bash 提交；反向亦然，错误语言返回 `422`。
  2. 存在至少一个 Python 与一个 Bash 的端到端示例题目与提交，均产生非空证据链。
  3. 代码中不存在把语言当作自由字符串解析的分支（必须来自受限枚举）。

### RQ-B-0-20 开发工具、开发语言、目标运行环境符合课程文档

- **原文**：开发工具、开发语言、目标运行环境需要符合文档"2026选件项目综合实践-课程开发项目：https://share.mubu.com/doc/1aK8gLOHdCV"。
- **归属**：全体。
- **规范解释（本项目落实方式）**：课程文档的外部约束在本项目内固化为下列**强制技术基线**，任何模块不得单方面替换：

  | 维度 | 冻结选择 | 理由 |
  |---|---|---|
  | 系统实现语言 | Python 3.12 | 课程规定对象语言，生态成熟 |
  | 脚本目标语言 | Bash 5.x | 课程规定对象语言 |
  | 前端 | TypeScript + React 19 + Vite 7 | 静态可交付、无自有后端 |
  | Web 框架 | FastAPI | 与 Pydantic v2 / OpenAPI 3.1 同源 |
  | 数据库 | PostgreSQL 17 | 单实例多 schema，权限可隔离 |
  | 消息中间件 | NATS JetStream 2.10 | 低内存占用，满足 512 MB 账本 |
  | 包管理 | uv（Python）、pnpm（Node） | 锁文件可复现 |
  | 容器/编排 | Docker + Compose v2 | 统一启动 |
  | 部署目标 | Linux（验收必须）；Windows 仅开发 | nsjail/cgroup v2 依赖 Linux |
  | 表格/文档导出 | 纯开源库（openpyxl 等） | 不引入商业组件 |

- **验收标准**：
  1. 五个项目的运行时版本声明一致（Python `>=3.12,<3.13`；Node 24；PostgreSQL 17；NATS 2.10）。
  2. 任何新增的技术栈替换都必须先有 MAIN ADR，并同步所有受影响模块的文档与锁。
  3. 完整功能验收必须在 Linux 环境执行；Windows 结果不得用于宣称运行时能力通过。

### RQ-B-0-30 必须能表达 Unix 操作系统作业

- **原文**：题目示例：Unix操作系统作业：https://share.mubu.com/doc/4iiznUkDHIF 。
- **归属**：全体（主要落在 B3 题目模型与 B2 Bash 执行链）。
- **规范解释**：题库模型与评测模型必须能表达典型 Unix 作业形态，至少覆盖：
  - 命令行参数 + stdin 驱动的 shell 脚本；
  - 文件系统副作用（创建/修改/删除文件、目录树操作）；
  - 管道与文本处理（`grep`/`sed`/`awk`/`sort`/`wc` 组合）；
  - 权限与退出码语义（`exit N`、`test` 条件）；
  - Bash 语法合法性检查（`bash -n`）与静态规则检查。
- **交付物**：B3 三类 adapter 至少各有一个 Unix 作业示例；B2 支持"文件系统快照差异"作为证据。
- **验收标准**：
  1. 至少一道 Unix 作业题目端到端跑通，特征包括：命令行输入、文件产出、退出码判定。
  2. 文件类题目的评分证据中包含被修改文件清单与内容摘要，而不是仅比对 stdout。
  3. 参考答案与学生答案在同一环境下产生可比对的证据（同 runner policy）。

## 2. B1 UI 用户界面需求

B1 是**静态 Web 客户端**，无权威数据库。所有权威数据来自 B4（身份/课程/名单）、B3（题目）、B2（提交/评测/成绩）。

### RQ-B-1-10 同学信息管理，导入 pdf、xlsx 格式同学信息，包含姓名、学号、课程编号、课序号等

- **规范解释**：教师可上传 PDF 或 XLSX 名单；系统完成"解析 → 列映射 → 逐行校验 → 预览 → 人工确认 → 原子写入"。字段至少包含：姓名、学号、课程编号、课序号；可选：班级、邮箱。
- **归属**：B1 负责交互与预览；**解析与写入由 B4 承担**（B1 不得自行决定入库结果）。
- **接口**：`POST /api/v1/roster-imports`（B4）创建导入任务；`GET /api/v1/roster-imports/{roster_import_id}` 读取预览；`POST /api/v1/roster-imports/{roster_import_id}/confirm` 确认提交。
- **验收标准**：
  1. 能分别导入一份 PDF 与一份 XLSX 名单，渲染出逐行列映射预览与错误行标注。
  2. 列名不匹配时进入"列映射"步骤，**不自动猜测**；无法唯一映射时明确报错并允许人工指派。
  3. 存在重复学号、缺失必填字段时，预览中逐行标红并给出原因；确认后被拒绝的行**不静默丢弃**，必须出现在结果报告中。
  4. 未确认前数据库无任何名单写入（原子性）；确认操作可重放且幂等。
  5. 预览页面不得渲染出学号以外的敏感信息（如邮箱全量、身份证号等）。

### RQ-B-1-20 同学信息编辑功能，操作需要权限控制

- **规范解释**：具备权限的教师可编辑学生、课序、选课关系；编辑前进行权限判定，编辑后留审计记录。
- **归属**：B1 提供编辑交互并做**前端可见性控制**；**授权判定与落库由 B4 执行**（前端隐藏按钮不构成安全边界）。
- **验收标准**：
  1. 学生角色登录后，名单编辑入口不可见；且直接调用编辑接口返回 `403`（证明后端独立校验）。
  2. 助教/教师仅能编辑其授权课程作用域内的名单；跨课程编辑返回 `403` 且产生审计记录。
  3. 每次成功编辑在 B4 审计表中留下：操作者、目标、变更前后值摘要、时间、请求 ID。
  4. 编辑表单对并发修改有冲突提示（基于 `updated_at`/版本号），不静默覆盖他人修改。

### RQ-B-1-30 成绩显示，按班级、按课程显示课程成绩，提供查询功能

- **规范解释**：教师与学生按课程/课序维度查询成绩；支持单题成绩与总成绩、评测状态与查看逐项证据入口。
- **归属**：B1 展示；数据来自 B2 成绩查询接口（学生仅见本人）。
- **验收标准**：
  1. 教师可按课程 + 课序筛选，看到全班成绩列表与汇总统计（提交数、平均分、通过率）。
  2. 学生只能查询到自己的成绩，无法通过修改 `student_id` 参数越权（越权请求返回 `403`）。
  3. 成绩列表中每一行可下钻到该次评测的逐项证据（规则/用例 → 得分/失分原因）。
  4. 未完成的评测以状态显示（`queued`/`running`/`failed`），**不以 0 分伪装成已完成**。
  5. 同名同姓学生以学号区分显示，不合并记录。

### RQ-B-1-40 作业题目显示，题干包含文字和图形

- **规范解释**：题目详情页渲染富文本题干（Markdown/HTML 安全子集）与图片；图片来自 B3 题目资源，经受控路径提供。
- **验收标准**：
  1. 题干中的加粗、列表、行内代码、代码块、表格、图片均可正确渲染。
  2. 图片以受控 URL 提供，未授权用户获取返回 `403`；响应头禁止脚本执行（无 `text/html` 伪装）。
  3. 富文本渲染不执行题干中的脚本或内联事件（XSS 测试用例必须被拦截）。
  4. 公开题目 DTO 中**不出现**参考答案、隐藏测试用例、expected output 字段（契约层与 UI 层双重校验）。
  5. 题目版本切换（历史版本查看）不改变已发布版本的渲染内容。

### RQ-B-1-50 作业答案提交，接收同学提交的作业答案，使用 API 接口发送到 B-2 模块

- **规范解释**：学生在题目页用代码编辑器编写并提交；提交经 `POST /api/v1/submissions`（B2）进入评测，前端展示实时进度（SSE）。
- **归属**：B1 采集与提交；B2 接收、校验、存储与评测。
- **验收标准**：
  1. 提交请求携带 `question_version_id`、`course_id`、`section_id`、`idempotency_key`；同一幂等键重复提交返回同一 `submission_id`，不产生重复评测。
  2. 超过题目声明的大小/文件数上限时，前端在提交前拦截并给出明确提示，后端同样拒绝（`422`）。
  3. 提交后进入状态机 `received → validated → queued → running → completed | rejected | failed`，前端进度与后端状态一致。
  4. 网络中断后重新打开页面可恢复未提交草稿（仅浏览器本地），**草稿不得被视为已提交**。
  5. 断线重连后 SSE 不重复展示历史进度（按 `event_id`/序号去重）。
  6. 学生提交他人课程/题目时返回 `403`。

### RQ-B-1-60 成绩导出，按班级、课程等形式导出成绩

- **规范解释**：教师按课程 + 课序 + 时间范围导出成绩，格式为 XLSX/CSV；导出内容可配置列。
- **归属**：B1 触发与下载；导出生成由 B2 承担（成绩属 B2 权威数据）。
- **验收标准**：
  1. 导出文件包含：学号、姓名、课程编号、课序号、题目、得分、满分、提交时间、评测 ID。
  2. 以 `=`、`+`、`-`、`@`、制表符、回车开头的单元格值被转义（防 CSV/XLSX 公式注入），并有对应测试用例。
  3. 导出内容与页面查询结果在同一筛选条件下完全一致（同一次查询口径）。
  4. 学生角色调用导出接口返回 `403`。
  5. 导出文件名与响应头包含 UTF-8 声明，中文不乱码。

### RQ-B-1-99 生成并记录运行日志

- **规范解释**：B1 产生前端运行日志：用户操作轨迹（导航、提交、导出触发）、接口错误、渲染异常。
- **边界**：B1 是客户端，日志仅记录**非敏感**前端事件；不得打印令牌、源码、答案、学号明文之外的 PII。服务端权威日志由各后端模块各自产生。
- **验收标准**：
  1. 成功的提交、导出、导入操作各产生一条结构化日志（JSON 行），含 `timestamp`、`level`、`event`、`request_id`。
  2. 未捕获异常被上报并包含 `request_id`，可与后端日志关联。
  3. 生产构建中不输出调试级日志与源码内容；日志中不出现 token、参考答案。
  4. 日志上报失败不阻塞用户主流程（降级为本地缓冲 + 静默丢弃，且不得因此吞掉主流程异常）。

## 3. B2 代码管理需求

B2 是**评测唯一权威**：提交物存储、静态检查、安全性确认、动态执行、评分证据、详细报告、成绩导出。

### RQ-B-2-10 由 API 接口接收 B-1 模块发送的待测作业代码

- **规范解释**：实现 `POST /api/v1/submissions`，接收 B1 提交的代码文件集合；请求体遵循 `submission-envelope` 契约。
- **验收标准**：
  1. 请求体通过 JSON Schema 校验；缺字段、类型错误、路径不合规（`..`、绝对路径、反斜杠逃逸）返回 `422` 且不落库。
  2. 每个文件校验 `content_sha256` 与实际内容一致；不一致返回 `422`。
  3. 需要认证：无 token 返回 `401`；token 的课程作用域与请求 `course_id` 不符返回 `403`。
  4. 相同 `idempotency_key` 重复请求返回同一 `submission_id` 与 `202`，不产生第二次评测。
  5. 接收成功后发布 `autograder.v1.submission.accepted`，事件不携带源码内容。
  6. 单文件与总大小、文件数量上限被强制执行，超限返回 `413`/`422`。

### RQ-B-2-20 由电子邮件接收待测作业代码

- **规范解释**：实现 IMAP 收取适配器，把邮件附件归一化为同一内部 `SubmissionEnvelope`；无法唯一匹配学生或作业的邮件进入隔离状态，**不自动评分**。
- **验收标准**：
  1. 能从 IMAP 邮箱拉取带附件邮件，附件归一化为 `SubmissionEnvelope` 并走与 API 相同的校验与存储路径。
  2. 通过发件人地址 + 邮件主题/正文中的作业标识唯一匹配学生与题目；无法唯一匹配时进入隔离状态并记录原因，不产生评测。
  3. 邮件检查点（UID/UIDVALIDITY 或 `Message-ID`）持久化，重复拉取不产生重复提交（幂等）。
  4. 附件类型/大小受限；可执行文件、压缩炸弹被拒绝并记录安全事件。
  5. 邮件处理全过程不把邮件正文、附件原文写入日志。
  6. 存在"同一邮件重复投递"的重复消费测试用例。

### RQ-B-2-30 存储管理待测作业代码

- **规范解释**：待测代码以内容寻址方式存储（摘要为主键），元数据入 `b2` schema；支持查询、保留与清理。
- **验收标准**：
  1. 同一内容只存一份（按 SHA-256 去重），元数据记录提交归属。
  2. 存储路径由服务端生成，不接受客户端提供的路径；目录穿越测试用例必须失败。
  3. 可查询某次提交的完整文件清单与各文件摘要；原始内容读取受权限控制（学生只能读自己的）。
  4. 存储写入与数据库事务一致性有明确策略（先写内容、后写元数据；孤儿内容可被清理任务回收）。
  5. 保留策略可配置，清理操作有审计记录，且不删除仍被评测记录引用的内容。

### RQ-B-2-40 检查代码的静态合法性，记录评价结果，包含总体评价与细节评价

- **规范解释**：不执行代码的前提下检查语法与结构合法性。Python 使用 `ast` 解析，Bash 使用 `bash -n` 与结构化规则；输出"总体评价（通过/不通过 + 摘要）"与"细节评价（逐条规则：规则号、severity、位置、说明）"。
- **验收标准**：
  1. Python 语法错误被 `ast` 检出，报告包含行号与错误信息；Bash 语法错误由 `bash -n` 检出。
  2. 每条细节评价包含：规则标识、severity（`error`/`warning`/`info`）、文件、行/列、可读说明。
  3. 结果持久化并在报告中可复现；同一输入两次运行产生相同的规则集合与同一摘要。
  4. **静态高危结果阻断动态运行**，此时评测状态为 `rejected`，且报告中**不得**声称运行成功或给出 0 分当作通过。
  5. 静态检查在受限环境中执行，不导入执行待测模块（不允许 import 副作用）。

### RQ-B-2-50 测试代码的动态运行逻辑准确性，记录评价结果，包含总体评价与细节评价

- **规范解释**：在 nsjail 沙箱中按 B3 的 evaluation package 逐用例执行，比较实际输出与期望输出，记录逐用例证据。
- **验收标准**：
  1. 每个测试用例的细节评价包含：用例 ID、输入摘要、实际输出摘要（截断）、期望输出摘要、通过/失败、失败类别（超时/崩溃/输出不符/资源超限）。
  2. 比较规则遵循题目声明的策略（精确、忽略行尾空白、数值容差等），策略由 B3 package 提供且不可由学生代码影响。
  3. 超时后**整个进程树被清理**，不残留进程；单个用例超时不导致其他用例被跳过或伪造通过。
  4. 单次评测的资源限制（CPU/内存/输出/文件数/进程数）被强制执行；超限归入 `failed` 或该用例失败，并记录具体限制项。
  5. 同一提交重复评测在相同环境下产生同一分数与同一证据摘要（可重放性测试）。
  6. 不使用 shell 字符串拼接执行学生代码；启动参数为固定数组。

### RQ-B-2-60 评价过程与结果记录到数据库，按格式导出

- **规范解释**：评测运行、逐项结果、证据、报告持久化到 `b2` schema；提供按课程/班级导出。
- **验收标准**：
  1. `evaluation_run` 与 `evaluation_result` 记录包含：绑定摘要（提交摘要、题目版本、测试包摘要、runner policy）、时间戳、状态迁移历史。
  2. 状态机每次迁移都有记录，失败迁移保留错误类别与（脱敏后的）原因。
  3. 导出支持 XLSX/CSV，字段与 B1 成绩导出口径一致（同一查询语义）。
  4. 导出防公式注入；导出中不包含源码、参考答案、隐藏测试。
  5. 数据库写入失败不导致"报告已生成"的假象：报告生成的先决条件是结果已持久化。

### RQ-B-2-70 待测代码安全性确认

- **规范解释**：在执行前后进行安全判定：静态高危模式识别、执行期沙箱违规（尝试联网、越权写、提权、超资源）、以及结论落库。
- **验收标准**：
  1. 静态阶段识别的高危模式（如 `rm -rf /`、反弹 shell、`curl | bash`、读取 `/etc/shadow`、无限 fork）产生 `security_finding` 记录并阻断执行。
  2. 执行阶段沙箱违规（网络尝试、写只读路径、提权）被捕获为安全事件，评测标为 `rejected`（安全原因），区别于 `failed`（技术原因）。
  3. 沙箱禁网：任何外部网络访问失败且被记录（不允许静默成功）。
  4. 每次评测的安全结论可在报告中查询到，且能区分"未发现"与"未检查"（不得把未检查写成安全）。
  5. 存在恶意样本回归用例集，且全部被阻断。

### RQ-B-2-80 生成答案代码评价结果，包含总体评价与细节评价

- **规范解释**：产出行之有效的最终评价结果：总体评价（得分、满分、通过与否、摘要结论）+ 细节评价（逐规则/逐用例证据）；可导出、可申诉复核。
- **验收标准**：
  1. 报告结构包含：总体评价、静态细节、安全结论、逐用例细节、执行环境摘要、绑定摘要。
  2. 每一分（或每一扣分）都能追溯到具体规则或用例；不存在无法解释的分数（合计校验必须成立）。
  3. 报告可被重放：凭绑定摘要重跑得到同一分数。
  4. 报告对学生的可见范围不包含参考答案、隐藏测试、他人代码。
  5. 报告 JSON 通过 `evaluation-report` JSON Schema 校验。

### RQ-B-2-99 生成并记录运行日志

- **验收标准**：
  1. 结构化 JSON 日志，含 `timestamp`、`level`、`event`、`request_id`、`submission_id`/`evaluation_run_id`（存在时）、`producer=B2`。
  2. 日志中**不出现**源码内容、参考答案、隐藏测试、凭据、token、内部绝对路径；有脱敏规则测试。
  3. 评测全链路（接收 → 静态 → 安全 → 动态 → 报告）可凭 `correlation_id` 串联。
  4. 异常路径（沙箱启动失败、DB 不可用、NATS 不可用）都有明确日志与状态，不吞异常。

## 4. B3 题库管理需求

B3 拥有题库、不可变题目版本、assignment、参考答案、测试包、去标识化统计。**B3 不执行学生代码、不计算分数、不拥有评测证据。**

### RQ-B-3-10 题目包含题干，参考答案，测试用例

- **规范解释**：题目实体由三部分组成：题干（富文本 + 图片资源）、参考答案（受保护）、测试用例（受保护）。三者都绑定到不可变 `question_version`。
- **验收标准**：
  1. 一条题目可保存富文本题干与至少一张图片，并可保存参考答案（多语言）与多条测试用例。
  2. 公开 DTO（`GET /api/v1/questions`、题目详情）中**不存在** `reference_answer`、`hidden_cases`、`expected_output` 等字段；契约测试断言字段缺失。
  3. 内部 evaluation package 接口（仅 B2 可访问）返回完整用例，响应需服务间认证。
  4. 参考答案与隐藏用例的存储访问受独立权限控制（数据库层或对象层），普通查询无法读取。
  5. 题干图片通过受控资源接口提供，未授权访问返回 `403`。

### RQ-B-3-20 题库维护，按课程管理题目

- **规范解释**：题目按课程组织；教师可增删改题目、创建 assignment（作业集合）、发布不可变版本。
- **验收标准**：
  1. 题目与 assignment 均带 `course_id` 作用域；跨课程读取/修改返回 `403`。
  2. 发表后的 `question_version` **不可变**：任何修改必须产生新版本；尝试原地修改返回 `409`。
  3. 版本发布需要显式动作（`publish`），且发布前完成完整性校验（题干非空、至少一条用例、参考答案存在、adapter 声明合法）。
  4. 发布事件 `autograder.v1.question.version.published` 在发布成功后发出，事件不携带参考答案与隐藏用例。
  5. assignment 只能引用已发布版本，不能引用草稿。
  6. 已发布版本被历史评测引用时不可删除（返回 `409`），只能归档。

### RQ-B-3-30 题目答题情况统计，统计内容包含：题目答题情况，题目回答次数分布等

- **规范解释**：B3 消费 B2 的去标识化 `evaluation.completed` 事件，聚合出题目维度的统计；不读取学生源码。
- **验收标准**：
  1. 统计包含：**题目作答次数、通过率、得分分布、失败类别分布**。
     - **独立作答人数**不在 B3 的口径内：事件**禁止携带 `student_id`**（`../api/events.md` §3.4），
       没有身份就无从计算"独立人数"，由 B2 的成绩查询侧提供该口径（判定见
       `../contracts/changes/CHG-B3-0003-distinct-student-statistic.md`）。
     - **平均分**同样不在 B3 的口径内：B3 不存储分数原值，只存分桶计数；从计数还原的"平均分"
       是近似值，以权威口吻出现在教师界面比没有该指标更糟。平均分由 B2 从真实成绩行计算。
  2. 统计输入**仅来自去标识化事件**：事件 payload 中不含源码、答案、学生姓名；B3 代码中不存在对提交内容的读取路径。
  3. 事件重复投递不重复计数（按 `event_id`/`evaluation_run_id` 唯一键去重）。
  4. 词法/数值聚合可重建（可从事件流重放到相同的统计值）。
  5. 统计查询按课程/题目/时间范围过滤，响应时间在数据量 10 万事件量级仍可用（分页 + 预聚合）。
  6. 统计结果不暴露单个学生的成绩给无权限用户。
  7. `evaluation.completed` 的 payload 携带 `score`、`max_score` 与 `is_pass`：没有 `max_score` 分数
     无法分桶、没有 `is_pass` 通过率恒为空（同 CHG-B3-0003 裁决）。

### RQ-B-3-40 测试框架①：待测代码由命令行接收测试数据

- **规范解释**：stdin/argv adapter：用例声明命令行参数与标准输入，采集 stdout/stderr 与退出码。
- **验收标准**：
  1. adapter manifest 能声明：`language`、`args`（数组，非 shell 字符串）、`stdin`、期望 stdout/stderr 比较策略、期望退出码。
  2. package 编译结果包含 adapter 类型与参数摘要，B2 无需理解题目语义即可执行。
  3. 参数中的特殊字符不会被 shell 解释（注入测试用例必须失败）。
  4. 存在一个端到端 Unix/Bash 示例题目验证该 adapter。

### RQ-B-3-50 测试框架②：待测代码由文件读取测试数据

- **规范解释**：file I/O adapter：把 fixture 文件放入工作区，声明输入/输出文件路径与比较策略。
- **验收标准**：
  1. adapter manifest 能声明：输入 fixture 集合（含内容摘要）、待测代码应读取/产出的路径、产出文件比较策略（**存在性 / 内容摘要**）。
     - **文本差异不在本期范围**：它需要的不是多一个枚举值，而是一整套判定语义（比较单位、空白与
       行尾处理、编码与 BOM、缺失/多余文件各自算什么、差异容忍口径）。这些语义一旦进入契约就会被
       评分结果依赖，而评分必须确定性可重放（ADR-0005）。存在性与内容摘要已能表达"输出文件正确"，
       且都是无参数、可复算的。判定见 `../contracts/changes/CHG-B3-0001-file-comparison-granularity.md`；
       如后续需要，须先冻结上述口径，再走 P3 契约变更。
  2. fixture 内容以摘要绑定进 package，评测证据中记录 fixture 摘要。
  3. 路径限定在工作区内，绝对路径与 `..` 被拒绝。
  4. 存在一个端到端文件处理示例题目（含目录树操作）验证该 adapter。

### RQ-B-3-60 测试框架③：待测代码实现了某种调用接口，需要经过使用 import、include 等操作后才能调用并测试

- **规范解释**：callable adapter：声明模块/函数入口与调用参数，由 runner 以受控方式 import 后调用。
- **验收标准**：
  1. adapter manifest 能声明：模块名、可调用对象名、参数序列化方式（JSON）、返回值/异常比较策略。
  2. import/callable 解析在沙箱内、工作区路径下进行；禁止从任意绝对路径或网络加载。
  3. 待测代码的 import 副作用（写文件、发起网络、`sys.exit`）被限制与捕获，作为用例失败/安全事件，而非崩溃整个 runner。
  4. 存在一个 Python callable 示例题目端到端验证。
  5. 三种 adapter 共用同一 package 结构与校验入口；新增题型不修改 B2 runner 核心（扩展点测试）。

### RQ-B-3-99 生成并记录运行日志

- **验收标准**：
  1. 结构化 JSON 日志，含 `producer=B3`、`request_id`、`question_version_id`（存在时）。
  2. 日志与事件中不出现参考答案、隐藏用例、expectation 内容、学生源码。
  3. 发布失败、事件消费失败、统计聚合失败都有明确日志与状态，不静默。
  4. 日志脱敏规则有测试覆盖。

## 5. B4 数据库管理维护需求

B4 拥有身份、角色、课程、课序、选课、审计，以及 PostgreSQL/NATS 的运行期维护与模块注册表。

### RQ-B-4-10 维护数据库的正常运行

- **规范解释**：B4 负责 PostgreSQL 实例的可用性、角色与权限、schema 存在性、健康检查、备份与恢复演练。**物理表结构由各模块迁移定义**（见 ADR-0001）。
- **验收标准**：
  1. 提供数据库健康检查端点/探针；依赖不可用时 readiness 失败并指明具体依赖，不返回健康假象。
  2. 每个模块使用独立最小权限 login role，仅拥有本 schema 权限；跨 schema 访问被数据库拒绝（有拒绝测试）。
  3. 提供备份与恢复运行手册，并在本地执行过一次恢复演练、记录真实命令与结果。
  4. 迁移执行顺序与 head 有记录；MAIN 只记录所有权与 head，不复制 DDL。
  5. 禁止应用使用超级用户连接（有配置校验与测试）。

### RQ-B-4-20 维护消息中间件运行（按需）

- **规范解释**：NATS JetStream 的运行期维护：stream/consumer 创建、持久化、投递语义、DLQ、健康检查。"按需"意味着仅在存在事件消费需求时启用，且不可用时不阻塞核心同步流程。
- **验收标准**：
  1. 依据 `MAIN/contracts/asyncapi/events.yaml` 创建 stream 与 durable consumer；命名与 subject 与契约一致。
  2. at-least-once 投递；消费者按 `event_id` 去重，重复投递不产生重复业务效果（有重复消费测试）。
  3. 达到最大投递次数的消息进入 DLQ，并可查询与人工重放。
  4. NATS 不可用时：readiness 反映真实状态；同步 API 路径仍可工作；outbox 保留待发事件不丢失。
  5. 存储配额与保留策略被配置，占用计入资源账本（≤0.25 GB）。

### RQ-B-4-30 定义数据库表结构

- **规范解释**：B4 定义**表结构规范（强制标准）** + **平台自己的物理表**（`b4` schema）。规范是"定义"，各模块的物理表由其自身迁移实现并遵守该规范。
- **规范内容（必须成文且可校验）**：
  - 命名：表名复数 snake_case、列名 snake_case、索引 `ix_<table>_<cols>`、唯一约束 `uq_<table>_<cols>`、外键 `fk_<table>_<ref>`。
  - 主键：`<entity>_id UUID`（UUID v4），由所属模块生成，不可变。
  - 时间：`created_at`/`updated_at` 为 `timestamptz`，UTC；对外 API 使用 RFC 3339。
  - 软删除：仅在需要时使用 `deleted_at`，且必须说明查询含义。
  - 禁止：跨 schema 外键、跨 schema 视图、`public` 共享 ORM、枚举随意新增。
  - 迁移：每模块独立 Alembic 版本表（`alembic_version_<schema>`），一次迁移只做一件事，必须可回滚或明确说明不可回滚原因。
- **验收标准**：
  1. 规范文档成文（`MAIN/docs/database/ownership.md` + 各模块 `docs/database/schema.md`），并可通过自动化检查发现违规命名。
  2. `b4` schema 的平台表（用户、角色、课程、课序、选课、会话、审计）建成并通过迁移验证。
  3. 每个模块的 Alembic head 与 `module.yaml` 中的 `migration_head` 一致（有校验）。
  4. 存在"跨 schema 外键被拒绝"的实测证据。
  5. 所有表结构变更都有对应迁移文件，无手工改库。

### RQ-B-4-40 定义管理各模块间 API 调用接口

- **规范解释**：本需求存在**设计期 / 运行期**两半，必须明确切分以避免 MAIN 与 B4 冲突（见 ADR-0003）：
  - **设计期（MAIN 拥有）**：OpenAPI / AsyncAPI / JSON Schema 的**作者身份与版本权威**；接口变更规程；契约摘要门禁。
  - **运行期（B4 拥有）**：模块注册表 —— 发现已装载模块、暴露其 `descriptor`、聚合各模块健康、暴露路由/事件/能力清单查询端点，使"即插即用"在运行时可见可验证。
- **验收标准**：
  1. 运行期注册表端点可查询到全部已装载模块的：模块名、契约版本、`provides`/`requires`、routes、events、schema 归属、迁移 head。
  2. 注册表内容与各模块 `module.yaml` 及 SDK `descriptor` 三方一致（有校验；不一致时明确失败）。
  3. 缺失 capability、重复路由、契约摘要漂移导致 host 启动失败，且失败信息指明具体模块与原因。
  4. B4 **不得**自行修改或重新定义 MAIN 的 OpenAPI/AsyncAPI 契约内容；发现不一致时按变更规程提出。
  5. 注册表端点本身受权限保护（仅管理员/运维可读全量，公开只暴露模块存活）。

### RQ-B-4-50 实现用户管理 API 接口

- **规范解释**：认证（登录/刷新/退出）、用户与角色管理、课程/课序/选课管理、名单导入处理的 API。
- **验收标准**：
  1. 登录签发短期 JWT（Ed25519），暴露 JWKS；其他模块可本地验证 `iss`/`aud`/`role`/课程作用域。
  2. 刷新凭据只放在 `HttpOnly` + `Secure` + `SameSite` cookie 中，不出现在响应体与日志。
  3. 密码以强哈希（Argon2id 或 bcrypt）存储，绝不明文/可逆存储；有哈希算法测试。
  4. 角色至少覆盖：学生、教师、助教/管理员；权限判定在服务端执行，前端隐藏不构成安全。
  5. 用户管理 API（增删改查、角色分配）仅管理员可用；普通用户调用返回 `403` 并记录审计。
  6. 名单导入处理的预览与确认端点行为符合 `RQ-B-1-10` 的验收标准（原子性、幂等、逐行校验）。
  7. 登录失败有速率限制/锁定策略；错误响应不泄露"用户是否存在"。
  8. 审计表记录认证与管理类敏感操作。

### RQ-B-4-99 生成并记录运行日志

- **验收标准**：
  1. 结构化 JSON 日志，含 `producer=B4`、`request_id`、`user_id`（存在时）。
  2. 日志中不出现明文密码、JWT、刷新令牌、cookie 值、完整 PII；有脱敏测试。
  3. 认证失败、权限拒绝、数据库/消息中间件异常都有明确级别与原因。
  4. 迁移执行、备份、健康检查结果被记录，可用于运维追溯。
  5. 日志可通过 `correlation_id` 与 MAIN host 及其他模块的日志串联。

## 5B. 团队自选增量（`RQ-T-*`）

**这些不是课程需求列表里的编号。** 课程方的 32 条需求见上面第 2～5 节，其权威来源是
`课程项目需求列表.xlsx`（ADR-0002）。本节记录**团队自己追加**的能力：它们不替换、不削弱任何
一条 `RQ-B-*`，因此不需要改动需求基线，也不需要课程方重新审批。

编号规则：`RQ-T-NN`，`T` = team-authored；序号单调递增、不复用；**不得**与 `RQ-B-*` 混排，
也不得被当成课程需求出现在答辩材料里。

引入本方需求的决策依据是 [ADR-0009](../adr/ADR-0009-ai-assistance-two-track.md)（它部分取代了
ADR-0005：放开了"运行期不调用任何模型服务"与"LLM 不参与评语生成"，同时把分数轨的确定性原样保留）。

### RQ-T-10 出题期 AI 辅助

- **规范解释**：教师**编写题目时**可获得模型辅助（题目质量分析、比较策略建议、题干表述与歧义
  检查、难度初判）。产物是**建议**，由教师确认后才写入题库。
- **验收标准**：
  1. 辅助入口只在教师/管理员的出题流程内出现；学生视图不存在该入口，也没有读取路径。
  2. **AI 不直接写库**：任何辅助产物都要经教师显式确认才落库，且落库写入者是教师身份。
  3. 辅助可以读教师正在编写的题目全文，但**产物不得把参考答案、隐藏用例或期望输出复述到任何
     学生可见位置**（公开 DTO、事件、日志、导出）。
  4. 模型服务**默认关闭**；未配置时该功能显示"未启用"，且不产生任何出网调用。
  5. 每次辅助请求记录 provider 与 model 标识、prompt 模板版本、时间；日志中不出现题目受保护内容。

### RQ-T-20 评测评语轨（非确定性，不参与判分）

- **规范解释**：评测完成后，可另生成一条**教学式评语**，解释学生"哪里没通过、可能是什么原因"。
  它与分数**完全分离**：分数轨保持 ADR-0005 的确定性、可重放、可枚举要求不变。
- **验收标准**：
  1. **输入白名单**：评语生成只允许读已落库的**结构化证据**——逐用例结论与失败类别、静态规则
     命中、安全结论三态、分数构成（用例权重与得分）、题目的**公开**元数据。
     **禁止**读取学生源码、参考答案、隐藏用例、期望输出。有自动化断言证明生成路径没有源码入口。
  2. **不污染分数轨**：模型输出不进入分数、`evaluation_results`、`case_evidence`、`result_digest`、
     五元绑定摘要或成绩导出文件；关闭或删除评语轨后，重放同一提交得到**完全相同**的分数与证据。
  3. **provenance 可核验**：每条评语携带 provider、model、prompt 模板版本、生成时间。
  4. **显式标注**：API 与 UI 都标明"由模型生成、非确定性、不参与判分、不作为申诉依据"。
  5. **可重新生成**：重新生成不改变任何分数；生成失败只标记该条评语不可用，不影响分数轨与状态。
  6. **默认关闭**：学生可见性由课程配置决定，默认关闭；未配置 provider 时系统行为与
     ADR-0005 时期完全一致。
  7. 评语生成路径**无网**以外的副作用：不写 `b2` schema 之外的表，不触发重新评测。

### RQ-T-30 AI 评分参考（顾问性，与权威分数物理分离）

- **规范解释**：评测完成后，可在同一次生成中另得一个**顾问性**的分数建议，回答"如果按另一种
  判断，这次大概是多少分"。它与评语**同轨、同输入白名单、同一次生成**，但有自己的结构与自己的
  边界。引入依据是 [ADR-0014](../adr/ADR-0014-ai-advisory-score.md)（它正面回应了 `CHG-0011`
  刻意不设 `score` 字段的那条设计约束）。
- **归属**：B2（生成与存储）、B1（并列展示）。
- **验收标准**：
  1. **它不是分**：`advisory_score` 及其任何派生值**不得**出现在 `evaluation_results.score` /
     `is_pass` / `result_digest`、`case_evidence`、`evaluation-report` schema、
     五项绑定摘要、`/api/v1/grades`、`/api/v1/grades/export`、任何事件 payload。
     有自动化断言：`evaluation-report` schema 拒绝含该键的实例；成绩与导出响应中不存在该键。
  2. **访问路径本身说明它不是分**：契约里它是 `EvaluationCommentary` 的**子对象**，
     消费者只能写成 `commentary.advisory_score.score`，而不是平级的 `commentary.score`。
  3. **不污染分数轨**：删除评语表全部内容后重放同一提交，分数、逐项证据与 `result_digest`
     必须逐字节相同。
  4. **输入白名单与 `RQ-T-20` 完全相同**：同一次生成、同一份结构化证据，**禁止**读学生源码、
     参考答案、隐藏用例、期望输出。有断言证明生成路径没有源码入口。
  5. **`max_score` 由证据填入，不由模型生成**：它必须等于证据里各用例权重之和。
     模型只提供 `score`、`rationale`、`confidence`。
  6. **越界即失败，不截断**：模型返回的 `score` 为负或大于 `max_score` 时整次生成判为
     `failed`。截断会把"模型说了什么"悄悄改成"我们允许它说什么"。
  7. **显式标注**：`disclaimers` 必须含一条针对分数参考的说明；`advisory_score` 为 `null`
     时该标注仍然存在。B1 必须与权威分**并列**展示且样式不得让参考分显得更权威。
  8. **默认关闭**：与 `RQ-T-20` 共用 provider 配置与课程可见性策略，默认关闭；未配置 provider
     时无任何出网调用。
  9. **可重新生成**：重新生成不改变任何权威值（分数、证据、`result_digest`）。
