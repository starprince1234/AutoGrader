本文件是 **32 条课程需求** 的全局追踪入口：每条需求的责任模块、关联工作包、关联契约、验收位置与当前状态。

- **规范性需求来源**：`MAIN/课程项目需求列表.xlsx`（工作表 `AutoGrader作业代码自动评测系统`）。
- **权威解释与逐条验收标准**：[rq-catalog.md](rq-catalog.md)。
- **优先级**：用户明确决定 > XLSX > `课程开发项目-思维导图.pdf` > B3 旧材料（依据 [ADR-0002](../adr/ADR-0002-current-xlsx-requirements-baseline.md)）。

- **说明行处理**：XLSX 中"实现以下类型题目测试框架"（第 24 行）是 `RQ-B-3-40/50/60` 的共同前言，**不生成编号**；其余空白/说明行同理。

## 2. 追踪矩阵

**状态词汇**（固定，不得使用其他措辞）：`骨架` / `待实现` / `已完成` / `阻塞`。

> **状态列是生成的，不是手填的。** 本文件是**视图**，不是第二份事实源：每个需求的权威状态在
> **拥有它的模块**自己的 `docs/requirements/traceability.md` 里。生成与校验由
> `scripts/sync_requirement_status.py` 与 `host/src/autograder_host/checks.py` 的
> `requirement_status_drift()` 共同完成（**同一份实现**：脚本负责改写，门禁负责拦截），
> 两者不一致时门禁失败——因此这一列不可能再静默漂移。
>
> 这一列曾经是**手工快照**：Phase 00 填过一次就再没更新，等到四个模块都交付之后，32 行里有
> 31 行仍写着 `骨架`/`待实现`。评审打开的第一份文档会得出"什么都没做"的结论。
>
> **例外**：`RQ-B-0-*` 是"全体模块"需求，没有单一模块拥有者，由 MAIN 声明（技术基线归 MAIN），
> 因此这三行不参与生成与漂移比对。

## 5. 变更规则

1. **课程方更新需求表时**，严格按此顺序：
   1. 更新 [rq-catalog.md](rq-catalog.md)；
   2. 更新本文件（§1、§2、§3）；
   3. 更新 `MAIN/host/src/autograder_host/checks.py` 的 `check_requirement_baseline()`；
   4. 更新受影响模块的 `docs/requirements/traceability.md` 与 `docs/collaboration/workpackages.md`；
   5. 更新 `MAIN/docs/workstreams/B*.md`；
   6. **最后**才写代码。
2. **严禁**出现"文档中有、检查中没有"或"检查中有、文档中没有"的编号差集——三处（rq-catalog、traceability、checks.py）必须同步。
3. 需求**新增**需要同时决定：责任模块、工作包、关联契约、验收标准、是否需要契约变更。
4. 需求**删除**需要同时清理：契约中相关端点/字段、模块追踪表、工作包、测试用例、阶段文档。**不留兼容层。**
5. 任何归属**变更**（如 `RQ-B-2-70` 改归 B3）属于 P3 级变更，需要新 ADR + 契约主版本提升 + 全模块同步。
