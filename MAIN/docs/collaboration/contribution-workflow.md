# 日常协作流程

本文件规定**从"我要做一个需求"到"它被验收"的完整动作序列**，以及并行开发中最容易出乱子的几处的处理协议。

前置阅读：[../workstreams/](../workstreams/) 对应模块的任务书、[../requirements/rq-catalog.md](../requirements/rq-catalog.md)、[module-doc-spec.md](module-doc-spec.md)。

---

## 1. 一个需求的完整生命周期

```text
① 认领          →  ② 读契约        →  ③ 写文档骨架    →  ④ 实现
                                                          │
⑧ 归档阶段  ←  ⑦ 更新追踪与证据  ←  ⑥ 跑门禁  ←  ⑤ 写测试 ┘
```

### ① 认领

- 在本模块 `docs/collaboration/workpackages.md` 的**认领表**中登记：工作包 ID、认领人、状态、预计完成。
- 规则：
  - 一个工作包**同时只有一个认领人**（避免两人改同一片）。
  - 认领前确认该工作包的**依赖**状态：依赖只要求"契约已冻结"，**不要求**对方已实现。
  - 跨泳道的工作包若都需要改共享文件，先协调（见 §3）。

### ② 读契约（不要跳过）

必须确认：

- 本模块 `contracts.lock` 的 `contract_version` 与 `digest`；
- 与本需求相关的端点/事件在 `MAIN/contracts/` 中是否已存在；
- 本模块 `module.yaml` 的 `routes` / `events` 是否已覆盖将要实现的能力。

**如果契约里没有你需要的端点或字段**：**停下**，走 §4 的契约变更流程。**不要**先写代码再补契约，也不要自行定义字段。

### ③ 写文档骨架（契约先行、文档先行）

在动手实现前，先让文档承载设计：

- 本模块 `docs/requirements/acceptance.md`：该 RQ 的可验证验收（前置、步骤、期望、失败判定）；
- 本模块 `docs/testing/cases.md`：新增/更新对应用例项；
- 若涉及状态机、组件或边界变化：更新 `docs/architecture/**`；
- 若涉及表结构：更新 `docs/database/schema.md` 的**意图**（DDL 由迁移承载）。

**为什么文档先行**：文档是唯一能让队友（与其他三个模块）在不读你代码的情况下判断"你会做什么"的东西。先写文档能提前暴露接口冲突。

### ④ 实现

硬规则（各模块 `AGENTS.md` 有更细的版本）：

- 只改本模块的数据；不跨 schema、不导入其他模块代码。
- 不执行 shell 字符串；学生代码只在沙箱里跑。
- 不把源码/答案/隐藏用例/凭据/PII 写进日志、事件、导出。
- 不留 mock 交付路径、别名、双写、开关、降级路径。

### ⑤ 写测试（同一批次内）

- 优先**扩展最接近的现有测试**；不存在合理归属时才新建文件。
- 必须覆盖失败路径：不只是 happy path。
- 数据库验收用**真实 PostgreSQL**，不用 SQLite。
- mock 只用于隔离不可控外部服务，**不得**用来证明真实集成已通过。
- 每个安全相关修复都必须带回归用例（否则会复发）。

### ⑥ 跑门禁

```powershell
# MAIN（契约、文档、需求基线）
cd MAIN ; .\.venv\Scripts\python.exe -m autograder_host.checks

# 本模块（示例：B2）
cd B2 ; uv run ruff check . ; uv run pytest
```

门禁**真实通过**才算完成。未执行或失败的项**必须**写进阶段文档。

### ⑦ 更新追踪与证据

必须同步更新：

| 文件 | 更新什么 |
|---|---|
| `docs/requirements/traceability.md` | 该 RQ 的**状态**（`骨架`/`待实现`/`已完成`/`阻塞`）与证据位置 |
| `docs/phases/active/phase-NN-*.md` | **实际执行的命令、环境、结果**；未执行项及原因 |
| `docs/testing/cases.md` | 用例的"存在"列 |
| `docs/api/contract.md`、`docs/api/events.md` | 仅在提供/消费**关系**变化时 |
| `docs/database/schema.md`、`migrations.md` | 仅在表结构或迁移变化时 |
| `docs/README.md` | 索引或状态表变化时 |
| `docs/collaboration/workpackages.md` | 认领表状态 |

### ⑧ 阶段归档（仅在满足全部门禁时）

按 [../phases/README.md](../phases/README.md) 的 7 条归档门禁判断。**不得**仅因代码写完就归档；不满足的保持在 `active/` 并写明阻塞项。

## 2. 分支与提交约定

| 项 | 约定 |
|---|---|
| 分支命名 | **以需求号开头**：`rq-b-2-40-static-legality`、`wp-b4-a-schema-provisioning` |
| 一个分支的范围 | 一个工作包（或一个需求）；不要混合多个不相关改动 |
| 提交粒度 | 小步提交；契约变更**单独一次**提交，便于审计与回退 |
| 提交信息 | 说明**做了什么 + 为什么**；关联需求号或 CHG 编号 |
| 不提交的内容 | `.env`、凭据、数据库转储、生产数据、个人信息、构建产物、缓存、`node_modules`、`.venv` |

**当前阶段不创建远端、不建 CI、不建 PR 流程**（除非明确要求）。四个模块是独立的本地 Git 项目。

## 3. 共享文件冲突预防（并行最容易出事的地方）

有些文件天然被多人触碰，必须约定协议：

| 共享文件 | 谁碰 | 协议 |
|---|---|---|
| `plugin.py`（模块 descriptor） | 全体模块成员 | **同一时间只有一人**可改 descriptor；改后必须同步 `module.yaml` 并说明原因 |
| `alembic/`（迁移目录） | 模块内多人 | 迁移**串行**：一次只有一人加迁移；新增迁移前先拉取最新 head |
| 路由注册表（前端） | B1 三条泳道 | 由一人先建立路由骨架并冻结文件结构，其他人只填页面 |
| 生成的 API 客户端 | B1 全体 | 重新生成是**共享动作**，改动后需通知全体；不手工编辑生成物 |
| 错误码/常量模块 | 模块内 | 新增可，修改语义需说明并同步文档 |
| `docs/README.md`（索引） | 全体 | 增删/移动文档时**立即**更新，避免多人同时改（小步提交） |
| `MAIN/contracts/**` | **仅 MAIN** | 见 §4 |

**通用做法**：触碰共享文件前，在 `docs/phases/active/` 的阶段记录里**登记意图**（一行即可），完成后再更新。这比事后冲突便宜得多。

## 4. 什么时候必须走契约变更

**触发条件**（任一命中即必须走 [../contracts/change-protocol.md](../contracts/change-protocol.md)）：

- 需要一个契约里**不存在**的端点、字段或事件；
- 需要改变已有字段的**语义、必填性、默认值或比较策略**；
- 需要**删除或重命名**任何契约元素；
- 需要改变**状态机取值**或**失败类别枚举**；
- 需要改变**认证方式**或错误码语义；
- 发现契约与实现不一致（**不要**顺着实现改契约）。

**不触发的**：

- 只改你自己的实现，接口形状不变；
- 只改你自己的文档（走 [module-doc-spec.md](module-doc-spec.md) 直接更新）；
- 加你自己的内部函数、表、迁移（不动契约）。

**关键纪律**：契约变更对四条开发线都是**串行点**，因此要**成批**做、**提前**做，不要在工作中间临时加字段。

## 5. 越界判定（怎么知道有人踩线了）

| 越界行为 | 怎么发现 |
|---|---|
| 跨模块 import | 搜索 `import autograder_b2` 之类的跨模块导入 |
| 跨 schema 访问 | 数据库权限拒绝（自动化用例 INT-12） |
| 代管他人表 | 检查迁移文件是否创建了非本模块 schema 的表 |
| 修改他人契约 | 摘要门禁失败 + CHANGELOG 无对应记录 |
| 改动未同步文档 | 文档门禁 + 追踪矩阵与代码不一致 |
| 隐藏失败 | 阶段文档写"通过"但无命令与结果 |

**越界即缺陷**，不是"灵活处理"。发现时优先**回退到契约路径**，而不是让越界合法化。

## 6. 节奏与同步点

| 活动 | 频率 | 内容 |
|---|---|---|
| 契约冻结确认 | 每个工作包**开始前**一次 | 确认本工作包依赖的契约已冻结、无人正在改 |
| 门禁执行 | 每次改动后 | 本模块门禁 + MAIN 门禁 |
| 阶段记录更新 | 每次改动后 | 真实命令与结果 |
| 集成试跑 | 每个阶段收尾 | `runbooks/integration.md` 的 8 项即插即用验证 |
| 契约变更评审 | 按需（串行） | 走变更规程第 2 步的影响分析 |
| 阶段回顾 | 每个阶段结束时 | 产出缺陷清单与知识笔记（Phase 00 的 R-01…R-05 即此类产物） |

## 7. 冲突与分歧的处置顺序

1. **契约问题** → 以 `MAIN/contracts/` 为准；有疑义由 MAIN 判定（走变更流程）。
2. **需求归属问题** → 以 XLSX 为准（[ADR-0002](../adr/ADR-0002-current-xlsx-requirements-baseline.md)）；导图与之冲突时以 XLSX 为准。
3. **接口权威问题** → 设计期归 MAIN，运行期归 B4（[ADR-0003](../adr/ADR-0003-api-authority-and-runtime-registry.md)）。
4. **数据所有权问题** → 以 [../database/ownership.md](../database/ownership.md) 为准。
5. **实现方案的取舍** → 新建 ADR，必须写备选方案与被否原因。
6. **以上都无法覆盖** → 记录为"已识别但尚未决策的议题"（[../adr/README.md](../adr/README.md) 有该表），**在决策前任何模块不得单方面假定某一种做法**。

## 8. 明确禁止的行为

| 禁止 | 原因 |
|---|---|
| 直接改 `MAIN/contracts/**` | 破坏四方锁与门禁；契约只有 MAIN 作者身份 |
| 为了让检查通过而手填摘要 | 掩盖真实漂移 |
| 保留兼容层/别名/双写/开关/降级路径 | 双轨必然产生只有一条被测试到的隐性缺陷 |
| 用 mock 证明真实集成通过 | 证明的是 mock 的行为 |
| 用 SQLite 结果代替 PostgreSQL 验收 | 权限与事务语义不同 |
| 在 Windows 上宣称 Linux 专属能力已验收 | 沙箱与 cgroup 在 Windows 不存在 |
| 把"待实现"写成"基本完成" | 状态词只有四种 |
| 把失败隐藏或降级描述 | 归档门禁会拦截，且会误导后续阶段 |
| 修改别人的需求归属而不走 ADR | 属 P3 级变更 |
| 把密钥、源码、答案、PII 提交进仓库 | 安全事故 |
