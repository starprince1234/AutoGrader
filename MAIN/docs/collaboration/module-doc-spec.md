# 模块文档规范（MAIN 强制）

本规范规定 **B1 / B2 / B3 / B4 四个模块项目内部必须存在的文档集合、每份文档必须回答的问题、统一格式与写作规则**。

任何一个模块的开发者（含新加入的同学、以及 AI Agent）**只打开本模块目录**，就应当能：理解范围、找到契约、装好依赖、跑通检查、认领需求、知道什么叫"做完"。因此模块文档是**自足**的，但**不重复定义契约字段**。

---

## 1. 三条铁律

### 铁律一：单一权威（Single Source of Truth）

每个事实只有一个权威位置，其他地方只做摘要 + 链接。

| 事实类型 | 权威位置 | 模块文档允许做什么 |
|---|---|---|
| 需求编号、原文、验收 | `MAIN/docs/requirements/rq-catalog.md` | 摘要引用编号，可写本模块的**实现级**验收细则 |
| HTTP/事件/JSON 字段 | `MAIN/contracts/**` | **禁止**手抄字段定义；只写"我提供/我消费哪些端点与事件" |
| 契约版本与摘要 | 各自 `contracts.lock` | 引用文件，不写死字面值 |
| 物理表结构 | 本模块 `alembic/versions/**` | 文档写表意图、约束、生命周期；DDL 以迁移为准 |
| 路由/事件/能力声明 | 本模块 `module.yaml` | 文档摘要，以 `module.yaml` 为准 |
| 跨模块边界与不可逆决策 | `MAIN/docs/adr/**` | 引用 ADR 编号 |
| 阶段完成证据 | 本模块 `docs/phases/**` | 必须写**真实执行过的命令与结果** |
| 资源账本与安全门禁 | `MAIN/docs/architecture/**`、`MAIN/docs/testing/**` | 落地为本模块的检查项 |

**禁止**：在模块文档中复制 OpenAPI 路径、请求体字段表、JSON Schema 属性列表、数据库 DDL。复制必然漂移。

### 铁律二：不得声称未实现的能力

初期各模块只有骨架（插件注册 + 配置校验 + 健康检查）。文档必须严格区分三种状态，并在标题或表格列中显式标注：

- `骨架`：代码存在并可运行，但只有非业务能力（注册、健康、日志）。
- `待实现`：已规划、有契约、有验收标准，但没有可运行代码。
- `已完成`：有可运行实现 + 通过真实测试 + 有阶段证据。

不允许写"应该可用""理论上支持""已基本完成"。不允许把 mock、测试收集、静态检查描述为运行时功能已验证。

### 铁律三：失败与缺口必须留在文档里

未通过的验证、外部依赖阻塞、跳过的工作项**不得**被隐藏或降级描述。留在 `docs/phases/active/` 中并写明：已确认事实、阻塞原因、恢复验证所需操作。

## 3. 每份文档必须回答的问题

写作时用这些清单自检。缺项即为文档不完整。

### `AGENTS.md`（40～80 行，不超过 100 行）

面向 AI Agent 的**执行规则**，不是百科。必须含：

1. `## 开始任务前`：要读哪些文档（具体路径）、要确认契约版本、要检查 Git 状态。
2. `## 我负责什么 / 不负责什么`：边界，用"我拥有 X；我不拥有 Y（属于 Z 模块）"句式。
3. `## 硬规则`：安全、数据、日志、事件、禁止事项（禁止 mock、禁止兼容层、禁止跨 schema、禁止 shell 字符串执行等）。
4. `## 文档同步`：改代码时同步更新哪些文档。
5. `## 验证`：本模块必须跑通的命令（真实可执行）。
6. `## 契约变更`：发现契约不一致时的正确处理流程（引用 MAIN 变更规程）。

**禁止**在 `AGENTS.md` 中放：完整表结构、API 字段表、长命令清单、历史过程、教程内容。

### `README.md`（60～150 行）

面向第一次进入的人：

1. 一句话定位 + 当前状态（骨架/部分实现/完成）。
2. 已实现能力 / 明确非目标（分两段写清楚）。
3. 在本系统中的位置（一张小型 ASCII 图）。
4. 前置条件：语言版本、工具、环境变量（指向 `.env.example`）。
5. 安装 / 迁移 / 启动 / 验证：**可复制执行**的命令块（Windows PowerShell 与 Linux 各给一份，若不同）。
6. 用户或开发者入口：本模块提供什么（HTML 路由 / API 前缀 / CLI）。
7. 文档入口：链接 `docs/README.md`。
8. 已知限制（必须真实；不得把未实现写成可用）。

### `docs/README.md`（唯一索引，30～80 行）

两张表：

- **权威表**：主题 → 权威文件 → 作用（覆盖上面清单的每一类）。
- **状态表**：文档/能力 → 状态（`骨架`/`待实现`/`已完成`）→ 最后验证方式。

规则：不在索引中的正式文档视为治理缺陷；新增/移动/归档文档必须同步更新索引。

### `docs/requirements/scope.md`

- 范围：本模块交付什么。
- 非目标：明确不做什么（这条最重要，防止越界）。
- 角色与用例：谁用、怎么用。
- 上游输入 / 下游输出去向。
- 术语（可链接 `collaboration/glossary.md`）。

### `docs/requirements/traceability.md`

必须是一张**逐 RQ 的追踪表**，列固定为：

| RQ | 需求摘要 | 本模块实现方式 | 关联工作包 | 关联测试 | 状态 | 证据位置 |

- `RQ` 必须精确匹配 `MAIN/docs/requirements/rq-catalog.md`；不得有该模块范围内的遗漏。
- `状态` 只能是 `骨架` / `待实现` / `已完成`。
- `已完成` 行必须能指向真实测试与阶段证据。

### `docs/requirements/acceptance.md`

逐 RQ 的可验证验收标准（比 MAIN 目录更贴近实现）：前置条件、操作步骤、期望可观测结果、失败判定。允许用 Gherkin 风格（Given/When/Then），但**必须可执行**。

### `docs/architecture/overview.md`

- 本模块在整体架构中的位置（上下文级）。
- 内部层次与依赖方向。
- 主要数据流（文字 + ASCII/Mermaid 图）。
- 与其他模块的交互方式（HTTP / 事件 / 无交互），并明确"我从不导入它们的代码"。

### `docs/architecture/components.md`

- 组件清单：职责、输入、输出、依赖。
- 扩展点（例如 B3 的三种测试 adapter、B2 的 runner 接口）：如何新增一种而不改核心。
- 明确"核心不改、扩展可加"的边界。

### `docs/architecture/models.md`

至少包含与本模块相关的：状态机（含状态、迁移、触发者、失败迁移）、关键时序（sequence）、数据流/生命周期。图用 Mermaid 或 ASCII，必须与代码状态常量一致。

### `docs/architecture/boundaries.md`

- 信任边界：谁能调用我、我信任什么、我不信任什么（一切外部输入）。
- 数据边界：我只读写哪个 schema；我禁止触碰什么。
- 安全边界：密钥来源、日志脱敏范围、导出限制。

### `docs/api/contract.md`

- 我**提供**的端点清单（方法 + 路径 + 用途 + 认证要求 + 作用域要求）。
- 我**消费**的端点/事件清单。
- 权威链接：指向 `MAIN/contracts/**` 与 `contracts.lock`。
- 错误约定：RFC 9457 Problem Details、UTC RFC 3339、UUID、`traceparent` / `X-Request-ID`。
- **不写字段表。**

### `docs/api/events.md`

- 我发布的事件：subject、触发时机、payload 语义摘要、是否含敏感数据（必须为否）。
- 我订阅的事件：subject、消费语义、去重键、重试与 DLQ 策略。
- 幂等与顺序假设的说明。

### `docs/database/schema.md`

- 表清单：表名、用途、关键约束、生命周期（谁创建、谁清理）。
- 私有/敏感数据标记（哪些列属于受保护内容）。
- 归属声明：只使用本模块 schema；禁止跨 schema 外键/SQL/ORM。
- B1 必须明确写"无权威数据库"，并说明浏览器本地允许保存什么、禁止保存什么。

### `docs/database/migrations.md`

Alembic 约定：版本表名、命名格式、一次迁移一件事、可回滚性、head 与 `module.yaml: database.migration_head` 的一致性要求、生成与执行命令。

### `docs/testing/strategy.md`

- 测试分层与各自目标（单元 / 契约 / 集成 / 端到端 / 安全 / 资源）。
- 每层必须覆盖的风险（不是按文件机械建测试）。
- 使用真实基础设施的要求：PostgreSQL 不得用 SQLite 代替；mock 只允许隔离不可控外部服务。
- 门禁命令（可复制）：lint、类型检查、迁移验证、测试、构建。
- 明确哪些检查目前在骨架阶段**尚不能执行**及原因。

### `docs/testing/cases.md`

测试用例目录表：用例 ID、目标 RQ、层次、前置、步骤要点、期望结果、当前是否存在（存在/待建）。这张表是"能不能证明需求被满足"的检查单。

### `docs/adr/`

`README.md` 索引 + 至少一条真实 ADR，格式固定：

```md
# ADR 0001 决策标题
- 状态：提议 / 接受 / 取代 / 拒绝
- 背景：需要解决的具体问题与约束
- 决策：最终选择及适用边界
- 后果：获得什么、付出什么、遗留什么风险
- 关联：需求、接口、迁移、测试或被取代的编号
```

候选主题（按模块实际情况选择，不要为写而写）：B1 无权威数据与草稿边界；B2 静态检查工具选型与 sandbox 策略；B3 不可变版本与 package 编译；B4 JWT/JWKS 与会话凭据存放。

### `docs/runbooks/local-development.md`

**每条命令都必须真实可执行**（在能执行的环境里跑过）。含：环境变量、装依赖、迁移、启动依赖服务、启动本模块、验证 readiness、跑测试、常见端口/路径说明。

### `docs/runbooks/troubleshooting.md`

症状 → 可能原因 → 处置步骤 → 如何确认已恢复。只写**真实遇到过或可确定**的问题，不要编造。

### `docs/phases/active/phase-NN-*.md`

固定小节：`目标与范围` / `输入与决策` / `完成条件` / `实际变更` / `验证记录`（真实命令 + 环境 + 结果 + 未执行项及原因）/ `风险与遗留项` / `文档影响检查`。

归档门禁（只有全部满足才能移到 `archive/`）：完成条件全部满足、静态检查与必要测试真实通过、API/数据库/架构/测试/README/运行手册已同步、没有隐藏的失败、遗留风险已记录且不构成完成条件。

### `docs/phases/archive/README.md`

阶段索引：阶段名、结论、完成日期、后续阶段链接。归档文件原则上不再改写。

### `docs/collaboration/onboarding.md`

**冷启动验收的载体。** 必须让一个不了解项目的人在 30 分钟内完成：读三个文件 → 装依赖 → 跑通门禁 → 说出本模块契约版本 → 认领一个工作包。写成"第 1 步/第 2 步…"的可执行路径，并写明每步的**成功标志**。

### `docs/collaboration/workpackages.md`

把本模块的 RQ 拆成 **2～3 人可并行认领**的工作包：

- 工作包 ID（`WP-B<模块>-<泳道><序号>`）、覆盖 RQ、目标、输入、产出、依赖（哪些包必须先完成或只需契约已冻结）、验收、预估工作量、建议认领人数。
- 明确"并行前提"：哪些接口必须先冻结，谁冻结，冻结后其他人不得再改。
- 一张**认领表**列（工作包 / 认领人 / 状态 / 预计完成），初始留空。

### `docs/collaboration/interfaces.md`

- 与 MAIN：我发布/消费什么、锁定哪个契约版本、摘要漂移时怎么办。
- 与每个邻居模块：**我依赖它什么、它依赖我什么**、失败时的行为（降级/报错/排队）。
- 一张"接口契约冻结清单"：接口名、owner、当前状态（冻结/未冻结）。

### `docs/collaboration/definition-of-done.md`

本模块"一项需求算完成"的检查清单：代码、测试、迁移、文档、追踪表、阶段记录、契约一致性、安全与脱敏自检、无 mock 残留。每条给出**可核验动作**。

### `docs/collaboration/glossary.md`

本模块专有术语（不必重复 MAIN 全局术语表，可链接）。

### `docs/knowledge/README.md`

收录标准（同一根因至少出现两次且有稳定修复）+ 命名规则 `YYYY-MM-DD-short-problem.md` + 模板（现象 / 重复触发条件 / 根因 / 最终修复 / 预防措施 / 关联证据）+ 当前笔记索引（初始为空表也要有表头）。

## 4. 写作规范

1. **语言**：中文为主，技术名词保留英文（`schema`、`adapter`、`traceparent`）。文件必须 UTF-8。
2. **不要"最后更新"字段**：无意义的日期字段会漂移。用阶段文档记录时间。
3. **区分四种陈述**并在措辞上体现：已验证事实（可指向命令/测试）、设计决策（可指向 ADR）、合理假设（写明是假设）、待确认事项（写明找谁确认）。
4. **状态词统一**：只使用 `骨架` / `待实现` / `已完成` / `阻塞`。
5. **图**：优先 Mermaid；简单结构用 ASCII。不得贴外链图片。
6. **相对链接**：文档间用相对路径链接，确保在任何克隆位置都可用。
7. **不写教程**：不要解释 Python/React 基础；写本项目的决定。
8. **篇幅**：每份文档以"能回答它该回答的问题"为准。典型 40～200 行；`rq-catalog` 类清单可更长。**禁止灌水式复述**。
9. **不得复制 MAIN 契约字段表**（见铁律一）。
10. **不得声称未实现能力**（见铁律二）。

## 5. 契约摘要的使用方式

模块文档中引用契约时，只允许下列写法：

```md
- 契约权威：`../MAIN/contracts/`（本地集成时）；版本与摘要见本仓库 `contracts.lock`。
- 我提供的端点：`POST /api/v1/submissions`、`GET /api/v1/evaluation-runs/{evaluation_run_id}/events`
- 我发布的事件：`autograder.v1.submission.accepted`
- 我订阅的事件：`autograder.v1.question.version.published`
```

**不允许**的写法：

```md
❌ POST /api/v1/submissions 请求体：
   { "student_id": "uuid", "question_version_id": "uuid", "files": [...], ... }
```

（字段属于 MAIN 契约；需要看字段时打开契约文件。）

- [ ] `docs/README.md` 的权威表覆盖每一类文档。
