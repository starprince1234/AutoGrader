# 项目初始化与项目文档管理

## 使用说明

这是一份可直接交给代码 AI 执行的项目初始化与文档治理规范。将本文件放入或拖入目标软件项目，并告诉 AI：

> 阅读并执行《项目初始化与项目文档管理》。先调查目标目录与需求材料，再完成项目初始化、文档体系建设和最终验证。除非遇到无法从环境中确认、且会实质改变结果的决策，否则不要只给计划或停下来询问。

本文不预设编程语言、框架、数据库或部署平台。AI 必须先从需求、现有代码、团队约束和运行环境中确定这些事实。若目标目录为空且技术选择会影响长期架构，AI 应给出推荐方案并向用户确认，不得静默替用户作出高影响决策。

## 一 交付目标

AI 的最终交付必须同时满足以下条件：

1. 项目目录可以被新的开发者或新的 AI 快速理解、启动、修改和验证。
2. 根目录存在简短有效的 `AGENTS.md`，用于规定工作规则和指向项目知识。
3. 根目录存在面向开发者的 `README.md`，包含项目定位、边界、启动、验证和文档入口。
4. `docs/` 是项目文档的统一入口，需求、架构、API、数据库、测试、阶段、决策和知识笔记均可追踪。
5. 代码、配置、迁移、契约、测试和文档之间不存在已知冲突。
6. 阶段只有在真实完成并通过约定验证后才能归档；阻塞或失败状态不得包装成完成。
7. 不创建用户未要求的兼容层、降级逻辑、模拟实现、占位业务代码或额外平台。

## 二 执行原则

### 2.1 先调查再修改

AI 在写入文件前必须完成一次只读调查：

- 查找并完整读取适用的 `AGENTS.md`、`AGENTS.override.md`、README、贡献指南和架构文档。
- 检查 Git 根目录、当前分支、工作区状态和用户未提交修改。
- 使用快速文件搜索确定语言、包管理器、入口、测试、迁移、CI 和部署配置。
- 阅读用户提供的需求文档、接口材料、数据模型和验收条件。
- 检查本机所需运行时和工具是否可用，但调查阶段不启动服务、不运行项目业务代码。
- 区分已有项目、空目录和只有材料或临时脚本的目录，不能把材料处理脚本误认为业务代码。

能从仓库和环境确认的事实不得询问用户。只有以下信息缺失时才询问：

- 产品范围或成功标准存在多种实质不同的解释。
- 空项目的技术栈、数据所有权或外部系统边界尚未决定。
- 继续执行需要新增付费资源、生产副作用、外部账户权限或破坏性数据操作。

每轮问题只询问会改变实现方案的关键决策，并附带推荐选项与影响说明。

### 2.2 以新需求为准

- 需求发生变化时，重新分析目标、数据流、调用链和架构影响。
- 被新需求替代的旧接口、旧配置、旧分支、旧兼容层、旧文档和旧测试必须删除。
- 除非用户明确要求，不得保留新旧双轨、别名、隐藏开关、自动降级或迁移兼容层。
- 外部系统尚未提供真实契约时，只记录边界和阻塞，不伪造对方系统或把 mock 当成交付。

### 2.3 保护用户工作

- 保留并避开用户已有的未提交修改。
- 未经明确要求，不执行 `commit`、`push`、创建远端、创建 PR、强制 checkout、hard reset 或清理工作区。
- 移动、覆盖或删除已有文件前，先确认其用途和精确路径。
- 不输出、提交或记录密钥、令牌、个人信息、生产数据和数据库转储。

## 三 项目初始化流程

### 3.1 确认项目契约

根据需求和调查结果，先写明并锁定：

- 项目目标、主要用户和可验证的完成条件。
- 首期范围、明确不做的内容以及外部系统边界。
- 技术栈、运行时版本、包管理器和依赖管理方式。
- 数据所有权、数据库类型、迁移工具和本地开发方式。
- 公共 API、消息或文件契约的权威来源。
- 测试层级、质量门禁、部署目标和安全边界。

如果这些内容来自用户确认，应写入架构决策记录或阶段文档，不能只留在聊天中。

### 3.2 整理根目录

已有项目优先遵循现有结构，不为形式重建目录。空项目一般至少包含：

```text
project-root/
├── AGENTS.md
├── README.md
├── .gitignore
├── .env.example
├── source-directory/
├── tests/
├── scripts/
├── docs/
│   ├── README.md
│   ├── requirements/
│   ├── architecture/
│   ├── api/
│   ├── database/
│   ├── testing/
│   ├── adr/
│   ├── runbooks/
│   ├── phases/
│   │   ├── active/
│   │   └── archive/
│   └── knowledge/
└── 语言和框架所需的构建或依赖文件
```

目录名应采用目标生态的惯例，例如 Python 的 `src/<package>/`、Java 的 Maven/Gradle 布局、Node.js 的现有应用结构。不得为了套模板而破坏框架约定。

### 3.3 建立版本控制和环境配置

- 若目标目录不是 Git 仓库且用户要求初始化项目，可执行本地 `git init`。
- 默认不创建首次提交、不配置远端、不建立 CI；这些操作需要用户明确要求。
- `.gitignore` 必须覆盖虚拟环境、依赖目录、构建产物、缓存、测试报告、编辑器临时文件、日志、`.env` 和本地数据库。
- `.env.example` 只列变量名、安全占位值和必要注释，不得包含真实密钥。
- 固定语言和工具链版本；使用该生态的锁文件保证依赖可复现。
- 新增生产依赖前确认其必要性，不引入与需求无关的框架、基础设施或抽象层。

### 3.4 建立可运行骨架

项目骨架至少应具备：

- 明确的应用入口和配置加载机制。
- 健康检查或等价的最小运行验证。
- 与生产一致的数据技术；禁止用行为不同的临时数据库替代正式数据库进行最终验收。
- 数据库迁移、结构化日志、统一错误响应和输入校验。
- 安全默认值：密钥来自环境变量、查询参数化、权限边界明确、错误响应不泄露内部信息。
- 真实能力对应的代码与接口；未纳入本期的能力不创建空实现或假数据路径。

## 四 AGENTS 文件规范

`AGENTS.md` 是给 AI 的项目级执行规则，不是项目百科全书。OpenAI 官方文档说明，Codex 会从全局位置向当前目录逐层读取指令，较深目录中的规则优先，默认合并上限为 32 KiB。因此：

- 根 `AGENTS.md` 只保存跨项目模块都适用的硬规则、边界和知识入口。
- 模块有特殊规则时，在对应子目录添加更具体的 `AGENTS.md` 或 `AGENTS.override.md`。
- 不把 API 字段、完整表结构、长命令清单和历史过程复制进 `AGENTS.md`；改为链接到 `docs/`。
- 规则写清需要检查的行为、正确路径和必要例外；格式化和 lint 细节交给工具配置。
- 新建或修改 `AGENTS.md` 后，当前 AI 应主动遵守其内容；新的 Codex 会话会在启动时重新发现指令。

建议根文件采用以下结构并按项目裁剪：

```md
# 项目规则

## 开始任务前
- 读取 `docs/README.md` 和与本次改动相关的需求、架构、接口、数据库、测试文档。
- 检查 Git 状态，保留用户未提交修改。

## 工程边界
- 写明本项目负责什么、不负责什么，以及关键安全或数据边界。

## 文档同步
- API、数据库、架构、测试和阶段变化分别更新对应文档。
- 阶段验收后归档；重复根因解决后创建知识笔记。

## 验证与交付
- 统一执行项目规定的静态检查、最小相关测试和必要构建。
- 报告真实命令与结果；失败或未执行项必须明确说明。
```

## 五 README 规范

根 `README.md` 服务于第一次进入项目的开发者，应按实际项目包含：

1. 项目名称和一句话定位。
2. 当前已实现能力与明确非目标。
3. 系统边界、主要组件和一张必要的简图。
4. 前置条件、语言版本、依赖工具和环境变量。
5. 可复制执行的安装、迁移、启动和验证命令。
6. API 或用户入口。
7. `docs/README.md` 链接。
8. 已知限制；不得把尚未完成的功能写成可用能力。

README 只保存长期有效的入口信息。阶段进度、事故过程和详细字段放在对应文档中，避免 README 变成历史堆积区。

## 六 文档知识体系

### 6.1 唯一导航入口

`docs/README.md` 必须列出每类文档的路径、用途、权威来源和当前状态。新增、移动、归档或删除文档时同步更新索引。不存在于索引中的正式文档应被视为治理缺陷。

### 6.2 文档类型与权威来源

| 变化类型 | 必须检查或更新 | 建议权威来源 |
|---|---|---|
| 需求、范围、验收条件 | `docs/requirements/`、追踪矩阵、阶段文档 | 已批准需求或 issue |
| 架构、模块边界、数据流 | `docs/architecture/`、ADR | 已接受 ADR 与当前代码 |
| HTTP、RPC、事件、文件格式 | `docs/api/`、契约测试、生成规范 | OpenAPI、Proto、JSON Schema 等机器契约 |
| 表、索引、约束、数据生命周期 | `docs/database/`、ERD、迁移 | 已提交迁移和当前 schema |
| 测试范围、门禁、环境 | `docs/testing/`、阶段验证记录 | 测试配置和可复现命令 |
| 启动、部署、恢复、排障 | `docs/runbooks/` | 经验证的操作步骤 |
| 跨模块的重要决策 | `docs/adr/` | 已接受 ADR |
| 当前阶段与完成证据 | `docs/phases/` | 实际 diff、命令和结果 |
| 重复问题的可复用结论 | `docs/knowledge/` | 根因分析和回归测试 |

### 6.3 防止文档漂移

- 为每种事实指定一个权威来源，其他文档只做摘要和链接。
- API 文档应由机器契约生成或与契约测试校验，避免手工维护两份字段定义。
- 数据库文档以迁移和实际 schema 为准；ERD 与迁移同批更新。
- README 中的命令必须在目标环境实际执行，不能凭记忆编写。
- 删除功能时同步删除对应文档、示例、配置和测试。
- 文档日期、状态和版本只有在项目确实需要时维护，不添加无意义的“最后更新”字段。
- 文档中区分已验证事实、设计决策、合理假设和待确认事项。

## 七 架构决策记录

当决策满足以下任一条件时创建 ADR：

- 会影响多个模块、公共接口、数据所有权或安全边界。
- 未来修改代价高，且存在多个可行方案。
- 替换既有架构或取消旧行为。
- 团队之后可能会问“为什么这样做”。

ADR 文件建议命名为 `ADR-0001-short-title.md`，内容为：

```md
# ADR 0001 决策标题

- 状态：提议、接受、取代或拒绝
- 背景：需要解决的具体问题和约束
- 决策：最终选择及适用边界
- 后果：获得什么、付出什么、哪些风险仍存在
- 关联：需求、接口、迁移、测试或替代此 ADR 的编号
```

ADR 记录决策，不记录日常实施流水。被新决策取代时标明新的 ADR，不静默重写历史结论。

## 八 阶段文档与归档

### 8.1 活动阶段

每个开发阶段在 `docs/phases/active/` 中只有一份主要记录，建议命名为 `phase-NN-short-title.md`。内容至少包括：

```md
# Phase NN 阶段名称

## 目标与范围
本阶段要交付的行为、接口或产物，以及明确不做的内容。

## 输入与决策
需求来源、关键假设、ADR 和外部依赖。

## 完成条件
可验证的功能、迁移、契约、测试和文档条件。

## 实际变更
完成后填写真实实现和受影响组件。

## 验证记录
逐项记录实际命令、环境和结果；未执行项说明原因。

## 风险与遗留项
只记录真实未解决问题、负责人或下一阶段入口。

## 文档影响检查
列出本阶段更新的 API、数据库、架构、测试和运行手册；无影响时明确写明。
```

### 8.2 归档门禁

只有同时满足以下条件才能将阶段文件移动到 `docs/phases/archive/`：

- 阶段完成条件全部满足。
- 代码自查、静态检查、必要测试和构建真实通过。
- API、数据库、架构、测试、README 和运行手册已经同步。
- 没有被隐藏、吞并或降级处理的失败。
- 遗留风险已明确记录，并且不构成该阶段完成条件的一部分。

如果环境、权限、外部接口或服务阻塞了验证，阶段保持在 `active/`，记录已确认事实和恢复验证所需操作。不得仅因为代码已经写完而归档。

归档时更新 `docs/phases/archive/README.md` 或阶段索引，记录阶段名称、结论、完成日期和后续阶段链接。归档文件原则上不再改写；纠正历史事实时保留修订说明。

## 九 知识笔记

知识笔记用于保存可复用的工程结论，不是日志仓库。只有同一根因至少出现两次，并且已经找到稳定修复和预防方法时才创建。

文件建议命名为 `YYYY-MM-DD-short-problem.md`，模板如下：

```md
# 问题名称

## 现象
用户可观察行为、错误信息和受影响范围。

## 重复触发条件
问题至少两次出现的环境、输入或操作条件。

## 根因
经过证据验证的技术原因；不要只写表面错误。

## 最终修复
采用的方案、关键实现和为什么能够消除根因。

## 预防措施
回归测试、静态规则、监控、运行手册或设计约束。

## 关联证据
代码、测试、issue、PR、ADR、日志片段或版本链接。
```

以下内容不应创建知识笔记：一次性拼写错误、尚未确认根因的猜测、单纯命令输出、可以直接从官方文档检索的常识、包含密钥或个人数据的现场信息。

## 十 测试与质量管理

- 测试覆盖实际风险，不为每个文件机械创建测试。
- 公共 API、序列化、数据库迁移、权限、安全边界、关键算法、并发和状态机必须有相应契约或集成测试。
- 优先扩展最接近的现有测试；不存在合理归属时才创建新文件。
- 最终测试使用与生产语义一致的基础设施。若正式使用 PostgreSQL，不得把 SQLite 测试结果当作数据库验收。
- mock 只用于隔离不可控外部服务，不得用来证明真实集成已经通过。
- 阶段文档记录实际运行的检查、环境、结果和未执行原因。
- 测试失败时集中分析根因，修复后只重跑失败检查和受影响的最小测试集，再执行必要的最终门禁。

## 十一 安全与依赖管理

- 所有外部输入通过类型化 schema 和白名单验证。
- 数据库访问使用 ORM、查询构造器或参数化查询，不拼接 SQL。
- 命令执行使用参数数组和允许列表，不把用户输入拼成 shell 字符串。
- 密钥和令牌只来自环境或正式密钥系统；示例值必须明显不可用于生产。
- 日志、错误响应和导出文件不得泄露密钥、答案、个人信息、堆栈或内部路径。
- 对外写操作必须有明确认证与授权边界；尚由网关或其他服务负责时，在架构和 API 文档中写明信任边界。
- 新增依赖应说明用途并锁定版本范围；不得为了方便引入重复框架。
- 依赖、镜像、数据库或云服务不可用时，报告阻塞，不擅自换成行为不同的替代品。

## 十二 统一最终验证

所有实现和文档完成后，再按项目风险集中执行：

1. 检查最终文件清单、Git 状态和 diff，确认没有覆盖用户修改或产生无关文件。
2. 运行 formatter 检查、lint、静态分析和类型检查。
3. 执行数据库迁移及迁移验证。
4. 运行最小但足够的单元、契约和集成测试。
5. 仅在编译型项目或交付要求需要时构建。
6. 仅在验收依赖运行时行为时启动应用，并在结束前停止临时服务和测试进程。
7. 重新生成 OpenAPI、schema、客户端或其他受控生成物，并检查是否与代码一致。
8. 检查文档链接、README 命令、中文 UTF-8、秘密泄露、阶段状态和文档索引。

任何命令未执行或失败都必须明确说明。不得使用“应该通过”“理论上可用”代替验证结果。

## 十三 AI 的最终汇报格式

AI 完成任务后，用简短、可核验的方式说明：

- 初始化或修改了什么，以及最重要的设计边界。
- `AGENTS.md`、README、文档索引和核心入口的位置。
- 实际执行的验证命令及结果。
- 未执行或失败的验证、具体原因和恢复验证的方法。
- 是否完成阶段归档；未归档时说明阻塞项。
- 真实存在的风险和限制。
