# ADR 0001 B5 是只读审计器：无数据库、无事件、无写入

- **状态**：接受
- **影响范围**：B5、MAIN 契约（`b5.yaml` 的状态码集合）、运维（部署与健康检查）

## 背景

B5 要回答的问题是"运行中的组合与契约声明是否一致"。实现这条能力时，有四个看起来"顺手就能加"的
选择，每一个都会把 B5 从观测面变成参与者：

1. **把报告存起来**（自己的 schema 或文件）——方便对比历史；
2. **发布"检测到不一致"事件**——让运维被动收到告警；
3. **同时做运行期注册表**（列出已装载模块的清单与健康）——和报告看起来很像；
4. **自动修复**（把差异写回契约或提示模块改名）——把发现变成动作。

同时，任务与项目规则要求"不新增生产依赖"，而视图 1 必须来自 `MAIN/contracts/openapi/*.yaml`、
端点必须按契约做 Bearer 认证。这两条与"零依赖"存在真实冲突，必须显式裁决而不是悄悄绕过。

## 决策

1. **B5 只读**：没有数据库 schema（`database.schema: none`）、没有迁移、不写文件、不发布事件。
   端点唯一的副作用是"读契约文件"与"读 `app.state`"。
2. **不实现运行期注册表**：那是 B4 的 `RQ-B-4-40`（ADR-0003）。B5 报告的是"契约 vs 运行组合"，
   注册表报告的是"已装载模块的清单与健康"。两者问的不是同一个问题，合并会让两个权威都不清楚。
3. **报告按需生成、不持久化**：任何缓存/留存都会造出第二份会过期的"一致性事实"。想要当前答案
   的人应当查询端点。
4. **保留三个真实依赖**（`pyyaml`、`pyjwt`、`cryptography`），并如实记录为对"零新增生产依赖"
   这一约束的偏离：
   - `pyyaml`：视图 1 必须解析契约 YAML；用正则解析结构化契约是被项目明令禁止的脆弱做法，
     而"从运行中应用反推契约"会让比对退化为自己跟自己比。MAIN 的门禁用同一解析器读同一批文件。
   - `pyjwt` + `cryptography`：契约声明 `security: bearerAuth` 与 `401`。B2 已用同一组合做同一件事；
     手写 JWT 验签是第三次实现安全关键代码（B3 的 RS256/EdDSA 混淆是一次真实事故）。
     去掉它们只能靠"不实现契约声明的认证"，那等于交付一个与自身契约不符的端点。
5. **认证不含授权分支**：契约规定"任何已认证主体可读"，因此没有角色/作用域判断。
   一个不执行的授权判断比没有判断更危险——它会被后续读者当成安全边界。

## 后果

**获得**

- 攻击面最小：无请求体、无路径参数、无查询参数、无写路径、无状态。
- 报告不可能成为第二份事实源，因此不存在"报告与门禁不一致时以谁为准"的问题。
- 三个依赖都是项目中已有的库（B2/B3/B4 的生产依赖），不引入新技术栈。

**付出**

- 无法回答"上周是否一致"：没有历史。需要历史时应由运维侧的采集解决，而不是让 B5 存状态。
- 验签需要 B4 的 JWKS 可达（loopback HTTP）。不可达时 fail closed（`401`），
  即"B4 挂了则一致性报告也读不到"——这是有意的：读不到报告好过读到一份未认证的报告。
- 三个新增生产依赖与本任务"不新增生产依赖"的要求冲突，已在阶段文档中记为**未满足项**，
  并给出上面逐条的理由，而不是把它写成"已满足"。

**遗留风险**

- 报告只比对路径/前缀，不比对方法与请求体 schema（两侧都只有路径可比）。
- 跨机部署仍未演练。`CONTRACTS_DIR` 的**默认值**现在经 SDK 的 `deployment_root()` 解析
  （读 `B4_MODULE_ROOT`，并校验该目录下确实存在 `MAIN/contracts`），只在源码树导入时回退到
  相对路径推导 —— 所以已安装形态不再依赖仓库布局。**这条是修好之后才成立的**：此前的默认值用
  `Path(__file__).parents[3]`，在 `site-packages` 里指向虚拟环境内部，本模块因此在集成宿主中
  一直报 `contract tree unreadable`；详见
  `../../../MAIN/docs/phases/active/phase-02-ai-activation-and-integration-repair.md` §2.1。
